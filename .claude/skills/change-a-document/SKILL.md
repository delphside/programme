# Changing a document

*One fact, one home* is a rule about where a fact belongs, and it is unusable
without knowing all the homes. There are hundreds of sections, so *"where does
this go?"* is answered by this procedure.

## The procedure

1. **Name the subject**: the *thing the sentence is about*, not the file you
   are in. "End-to-end tests only run on some branches" is about CI triggers,
   wherever you noticed it.
2. **Find its section.**
   - Which kind of document lives where: the layout in the programme's
     [root README](../../../README.md), and
     [2.1](../../../records/2.1-applications.md#what-each-applications-folder-holds)
     for each application's records.
   - Every heading of an application's own documents: its document map, where
     it has one, generated by `programme/scripts/docs/document-map.py`. Tile
     Lite Elite's is
     [`docs/4.1.6-document-map.md`](https://github.com/delphside/tile-lite-elite/blob/main/docs/4.1.6-document-map.md).
     The programme's own numbered documents have no map: search them as step 4
     says.
3. **Read that section before writing.** Most of the time the fact is already
   there, or half there, and the change is an edit.
4. **If you cannot find the section, search for it.** Search the documents
   (`grep -ri` on the subject's words, not yours), then name which of these it
   is:

   | Diagnosis | What it means | The fix |
   | --- | --- | --- |
   | **the map is wrong** | the section exists and the map, where there is one, does not show it | fix the map's generator, `scripts/docs/document-map.py`, in the programme repository, never from an application's pinned `programme/` |
   | **the structure is wrong** | it exists under a heading nobody would look for | rename or move the section |
   | **there is a gap** | nothing owns this subject | add a section to the document that owns the subject |

5. **Act on the diagnosis, and say it in the commit message.** Documentation
   changes go on without the owner (`CLAUDE.md` *The work*). Bring to him only:
   - a fact that still cannot be placed, because that blocks the work;
   - a change to a rule.

   Writing the fact where you are is never the answer.

## What belongs in it, once you have the right section

Write to [`docs/1.5`](../../../docs/1.5-writing-documents.md), the house
style, which the two document reviewers apply.

## Three homes that are easy to miss

- **A new application script** goes in the application's tools register,
  where it has one (its technical profile's `documents.tools_registers`; Tile
  Lite Elite's is `docs/4.3.0-tools.md`).
- **A new programme script** goes in
  [1.1](../../../docs/1.1-programme-tooling.md).
- **Every string the tooling matches literally** is in
  [1.6](../../../docs/1.6-github-project-board.md).

## When documents or code disagree

**Find how each side came about before changing either.** Each was written
for a situation, and the fix keeps both intents only once both are known.

1. Make sure the whole history of each side is present in its repository.
   From an application's checkout, a programme document's history is in
   `programme/` and a record's is in the live checkout. A shallow clone names
   its oldest commit as the one that added anything older, so fetch the rest
   where the clone is shallow:

   ```sh
   if [ "$(git rev-parse --is-shallow-repository)" = true ]; then git fetch --unshallow; fi
   ```

2. Find the commit that wrote each side, searching for a phrase that sits on
   one line, since `-S` matches literal text:

   ```sh
   git log --format='%h %ad %s' --date=short -S'<a phrase from that side>' -- CLAUDE.md docs .claude
   ```

   For code or a record, put its path after `--`. To follow a function in
   code, use `git log -L :<function>:<file>`.

   The programme repository carries the history from its first commit,
   including the rules' time in Tile Lite Elite under older names.
3. Read each commit's message (`git show -s <sha>`) and diff: what situation
   the change was written for, who decided it and which side changed last.
4. Write the fix from both intents, and say in the commit message where each
   side came from. A fix that changes a rule, or an application, goes to the
   owner as `CLAUDE.md` *The work* says.

## When `main` has changed the same text

When a rebase or a pull request shows that `main` has changed text your
branch also changes, follow
[1.2 *When `main` moves under a branch*](../../../docs/1.2-change-lifecycle.md#when-main-moves-under-a-branch):
redo your edit on `main`'s text, running this procedure again from step 1,
since the fact may now have another home or be there already.

## Traps

- **Renumbering breaks anchors, and the link checker catches only the linked
  ones.** Before renumbering, search for unlinked references to the old number
  (`grep -rn '§2.5'`) and update them. Renumber only when `check-docs.sh`
  passes (see *Checks*): it runs the link check and, where the application has
  a document map, its currency check.
- **A diagram's `.svg` is a build output.** Edit its source and re-render: the
  `.mmd` beside it, or for a generated diagram the script that writes it. Tile
  Lite Elite's `docs/diagrams/README.md` has the commands, and the Puppeteer
  failure to expect.
- **A semicolon ends a Mermaid statement.** `(Bearer token; wasm only)` broke a
  sequence diagram and rendered as an error box. Rephrase the label, or write
  the semicolon as `#59;`. Step 6 of `check-docs.sh` parses every diagram where
  `scripts/docs/mermaid` (`programme/scripts/docs/mermaid` from an application)
  has its packages installed; without them it
  says so and passes.
- **Two branches can both add `§2.5.1`.** Where the application has a map,
  `document-map.py` catches it once they meet. Before that, list the other open
  branches (`git branch -r`) and check each one's diff for the document
  (`git diff main...origin/<branch> -- <file>`).

## Checks

In an application's repository, where it has a document map, regenerate it,
check, and commit the regenerated map with the change:

```bash
programme/scripts/docs/document-map.py --write   # regenerate, and report duplicates
programme/scripts/docs/check-docs.sh             # every check; a stale map fails it
```

In the programme's repository, where the scripts are under `scripts/`, for its
own documents, `CLAUDE.md` and the skills:

```bash
scripts/docs/check-docs.sh --programme
```
