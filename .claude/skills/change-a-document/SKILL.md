# Changing a document

**Read this before adding text to a document, `CLAUDE.md` or a skill.**

*One fact, one home* is a rule about where a fact belongs, and it is unusable
without knowing all the homes. There are hundreds of sections, so *"where does
this go?"* is answered by this procedure, never by *"where I already am"*.

## The procedure

1. **Name the subject**: the *thing the sentence is about*, not the file you
   are in. "End-to-end tests only run on some branches" is about CI triggers,
   wherever you noticed it.
2. **Find its section.**
   - Which kind of document lives where: the programme's [root
     README](../../../README.md) layout, and
     [2.1](../../../records/2.1-applications.md#what-each-applications-folder-holds)
     for each application's records.
   - Every heading of an application's own documents: its document map (Tile
     Lite Elite's is
     [`docs/4.1.6-document-map.md`](https://github.com/delphside/tile-lite-elite/blob/main/docs/4.1.6-document-map.md)),
     generated by `programme/scripts/docs/document-map.py`.
3. **Read that section before writing.** Most of the time the fact is already
   there, or half there, and the change is an edit rather than an addition.
4. **If you cannot find the section, that is a finding.** Search the documents
   (`grep -ri` on the subject's words, not yours), then say which of these it
   is and propose the fix:

   | Diagnosis | What it means | The fix to propose |
   | --- | --- | --- |
   | **the map is wrong** | the section exists and the map does not show it | a fix to `document-map.py` |
   | **the structure is wrong** | it exists under a heading nobody would look for | rename or move the section, said in the commit |
   | **there is a gap** | nothing owns this subject | a new section in the document that owns the subject, with the reason in the commit |

5. **Ask the owner before acting on a diagnosis, and whenever you still cannot
   place the fact.** Renaming, moving or creating a section changes the shape
   of the documents. Writing the fact where you are is never the answer.

## What belongs in it, once you have the right section

[`docs/1.5`](../../../docs/1.5-writing-documents.md) is the house style: what
each range holds, who reads it, how it is written and where it differs from
Google's guide. Write to it; the two document reviewers apply it.

## Three homes that are easy to miss

- **A new application script** is registered in the application's tools
  register (its technical profile's `documents.tools_registers`; Tile Lite
  Elite's is `docs/4.3.0-tools.md`).
- **A new programme script** is registered in
  [1.1](../../../docs/1.1-programme-tooling.md).
- **Every string the tooling matches literally** is in
  [1.6](../../../docs/1.6-github-project-board.md).

## Traps

**Renumbering breaks anchors, and the link checker only catches the linked
ones.** Renumber only with `document-map.py --check` and the link check both
green.

**A diagram's `.svg` is a build output.** Edit its source and re-render: the
`.mmd` beside it, or for a generated diagram the script that writes it (Tile
Lite Elite's `docs/diagrams/README.md` has the commands, and the Puppeteer
failure to expect).

**A semicolon ends a mermaid statement.** `(Bearer token; wasm only)` broke a
sequence diagram and rendered as an error box. `check-docs.sh` step 6 parses
every diagram where `programme/scripts/docs/mermaid` has its packages installed;
without them it says so and passes.

**Two branches can both add `§2.5.1`.** `document-map.py` catches it once they
meet; before that, check what is in flight.

## Afterwards

In an application's repository, regenerate the map first, then check:

```bash
programme/scripts/docs/document-map.py --write   # regenerate, and report duplicates
programme/scripts/docs/check-docs.sh             # every check; a stale map fails it
```

In the programme's repository, for its own documents, `CLAUDE.md` and the
skills:

```bash
scripts/docs/check-docs.sh --programme
```

**Commit the regenerated map** with the change.
