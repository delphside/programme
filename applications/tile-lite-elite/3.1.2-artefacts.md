# 3.1.2 Tile Lite Elite artefacts

Tile Lite Elite's artefact register, in two parts: its artefacts by route, and
everything under change control that leaves no trace in git: files on
*the production host* (the Oracle VM that runs the service), resources in
Oracle Cloud Infrastructure (OCI), objects in GitHub and records held by
third-party services. Each entry carries enough to recreate it, or links to
where [4.3.4](https://github.com/delphside/tile-lite-elite/blob/main/docs/4.3.4-production-environment.md)
holds the detail.

## Artefacts by route

Every artefact of Tile Lite Elite, in the repository or outside it, falls under
one route. The rule is [1.2 §2.15](../../docs/1.2-change-lifecycle.md#route);
this is its answer here.

| Route | Tile Lite Elite's artefacts |
| --- | --- |
| Production Release | everything built into the image, deployed by `deploy.sh`: `crates/**`, `old-crates/**`, `Cargo.toml`, `Cargo.lock`, `.cargo/config.toml`, `rust-toolchain.toml`, the word lists, `Caddyfile`, `Dockerfile` and `docker-compose.yml`. On the production host, files under `/opt/tile-lite-elite/`, the systemd units and packages, all installed by the owner by hand |
| Application Tooling and Docs | the scripts in `scripts/develop/`, `deliver/`, `operate/` and `measure/`, except what is installed on the production host; `ci.yml`, `advisories.yml`, `e2e/**` and `.cargo/audit.toml` |
| Programme Tooling and Docs | the programme repository's scripts, git hooks and Claude hooks; `docs.yml` and the other workflows; the documents `documents.py` classes as programme |
| Other | the OCI console, GitHub settings, the host's [entries](#the-production-host) marked Other, and preview and rehearsal deploys |

The cases a reader might misplace:

- The production host's packages, its Docker daemon and the image's packages
  are the application's; the hypervisor is Oracle's.
- `wordlist-tools` and `scripts/develop/mkfavicon.py` are generators with a
  human step, so they are Application Tooling and Docs.
- `.cargo/audit.toml` configures `cargo audit` only. `.cargo/config.toml` is
  copied into the build and changes the bytes, so it is a Production Release.

**The rule in executable form is the technical profile's `ships.non_shipping`**
in
[`app-profile.toml`](https://github.com/delphside/tile-lite-elite/blob/main/app-profile.toml)
at the application's root: the paths that do not reach the image, as regular
expressions matched from the start of a path. A commit touching any other path
is an image change, whatever else it touches. This section is the authority for
what belongs in the list.

- The pre-commit hook asks `programme/scripts/board/board-shipping.py`;
  `deploy.sh`, `verify.sh` and CI ask it through `shipping-paths.sh`.
- `shipping.py` applies the list and holds no path.
- What counts as a version-only bump is the profile's `versions.bump`.
- The list covers the image only. The sources of the host's
  `/opt/tile-lite-elite/` files, in `scripts/` and `docs/`, take the Production
  Release route, and no tool checks them.

## The production host

Verified by the owner on the VM, 2026-08-21.

| Artefact | Route | What it is | Why it is not in the repository |
| --- | --- | --- | --- |
| `production:~/tile-lite-elite/docker-compose.yml` | Production Release | the compose file the running stack uses | **copied there by `deploy.sh`** from the repository — the copy is a deployment artefact, and the source of truth is in git |
| `production:~/tile-lite-elite/.env` | Other | the secrets and per-host settings Compose reads ([4.3.4](https://github.com/delphside/tile-lite-elite/blob/main/docs/4.3.4-production-environment.md#host-configuration-env)) | created by hand by the owner; holds secrets; `deploy.sh` leaves it alone |
| `production:~/.tile-lite-elite-backup-par` | Other | the write-only credential the nightly backup uses, mode `0600` | a secret ([4.3.4](https://github.com/delphside/tile-lite-elite/blob/main/docs/4.3.4-production-environment.md#the-nightly-copy-that-leaves-the-vm)) |
| `production:/opt/tile-lite-elite/` | Production Release | copies of `scripts/operate/backup-to-oci.sh`, `scripts/operate/check-log-hygiene-nightly.sh`, `scripts/operate/check-log-hygiene.py` and `docs/4.4.7-log-events.md`, which the nightly jobs run | **the owner copies them by hand in the delivery that changes them**: there is no checkout on the host, and nothing re-copies them, so a change to any of the four that is not re-copied leaves the host running the old version (delphside/tile-lite-elite#174) |
| `production:/etc/systemd/system/tile-lite-elite-{backup,log-check}.{service,timer}` | Production Release | the two nightly jobs and their timers, from `scripts/operate/systemd/` | the owner installs them by hand, like the `/opt` files |
| `production:~/tile-lite-elite/snapshots/` | Other | pre-deploy database snapshots, newest five kept | data, created by `deploy.sh` |
| `production:/etc/systemd/journald.conf.d/50-cap.conf` | Other | `SystemMaxUse=50M`, `RuntimeMaxUse=16M`. Its `SystemMaxUse` is overridden by `zz-tile-lite-elite.conf`; its `RuntimeMaxUse` is in force | applied by hand; journald runs on these values, not its defaults |
| `production:/etc/systemd/journald.conf.d/zz-tile-lite-elite.conf` | Other | `SystemMaxUse=100M`, `MaxRetentionSec=7d`. Named to sort last, since journald applies these files in name order and a later value wins | applied by hand |
| `production:` docker volumes `tile-lite-elite-data`, `-caddy-data`, `-caddy-config` | Other | the database, and Caddy's certificates and state | created by Docker, and the first is the only irreplaceable thing on the machine |
| `production:` iptables `INPUT` chain | Other | accepts established, ICMP, loopback and **22 only**; rejects the rest | applied by hand |

Docker publishes ports 80 and 443 through its own `DOCKER` chain in the `nat`
table, which bypasses `INPUT`. An edit to the host's compose file changes what
runs until the next deploy overwrites it.

## The deploying checkout

| Artefact | Route | What it is | Why it is not in the repository |
| --- | --- | --- | --- |
| `artifacts/<sha>.tar.gz` | Other | the built images for one commit, with a `.sha256` and a `.manifest` beside it. Newest five kept | **a cache, not a record.** Git-ignored, created by `deploy.sh` in the checkout it runs from, shared by rehearsal and production so both load the same bytes. Losing one costs a rebuild of that commit |

## GitHub

The repository's own GitHub objects. The programme's objects, the fields each
issue carries and the strings the tooling reads from them are
[1.6](../../docs/1.6-github-project-board.md).

| Artefact | Route | What it is |
| --- | --- | --- |
| `github:releases` | Other | published by `deploy.sh` for a `prod-X.Y.Z` tag, with auto-generated notes; a failed publish does not fail the deploy, so not every tag has one. Public |
| `github:ruleset default branch checks` | Other | requires CI's `check` job on the default branch; the owner's account bypasses it, which lets `deploy.sh` push the version bump |

## Exit statuses in Tile Lite Elite's scripts

The scheme is
[1.2 §2.13](../../docs/1.2-change-lifecycle.md#what-a-scripts-exit-status-means),
including `deploy.sh`'s `3`. `shipping-paths.sh` adds `70` when it cannot
decide what ships, and so do `deploy.sh`, `verify.sh` and CI, which source it.
Scripts report through the log events in
[4.4.7](https://github.com/delphside/tile-lite-elite/blob/main/docs/4.4.7-log-events.md).

## Not yet recorded

- **DNS** for `tileliteelite.com` and `rehearsal.tileliteelite.com`: the
  records exist, held where this register does not yet say
- **the rehearsal environment's host artefacts**: the same shape as
  production's
- **the rehearsal access gate**: the `Caddyfile` matcher ships with the image,
  and the key is in `rehearsal:~/tile-lite-elite/.env`, written by
  `scripts/deliver/rehearsal-access.sh`
- **the rest of the production host**, as built by 4.3.4 *Building a host*: the
  swapfile and its `/etc/fstab` line, the `docker` and `systemd-journal` group
  memberships, the installed packages, and the `sa` alias `deploy.sh` writes
  into `~/.bashrc`
- **the rest of OCI**: the security list's ingress rules, the notification
  topic `tile-lite-elite-alerts` and the backup's write pre-authenticated
  request

## What counts as an artefact here

The rule is
[1.2 §2.13](../../docs/1.2-change-lifecycle.md#what-counts-as-an-artefact-and-when-an-entry-appears).

- Artefacts: `deploy.sh` and `programme/.claude/hooks/turn-check.sh`.
- Not artefacts: test code, which is `scripts/tests/`, `crates/*/examples/`,
  and the programme repository's `scripts/board/tests/` and `scripts/tests/`.
