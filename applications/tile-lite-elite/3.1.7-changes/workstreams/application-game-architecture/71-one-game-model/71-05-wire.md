# 71 The wire

This is the first of two files on the wire, and it is read first. It holds what
today's wire does that is worth keeping and what to move away from, the model
(why the DTOs are invisible, who may see what, and the interface layer that sits
between the server and any client), and the technologies the model rests on:
serde, Cargo workspaces, and HTTP and WebSocket with axum.
[`71-05b-wire-types.md`](71-05b-wire-types.md) holds the types that cross the
wire: the seat, the game, structured descriptions, the envelope and the error
body. This file follows [`71-04-seats.md`](71-04-seats.md); the second is
followed by [`71-06-engine.md`](71-06-engine.md).

## As-is

Worth keeping:

- **One authorization check for every route and the WebSocket.**
  `resolve_viewer_access` (`server-game/src/game_state.rs`) is used by every
  handler that returns a game and by `game_events`, so the rule cannot drift
  between them.
- **Redaction where the data leaves the server.** `to_dto` is full fidelity,
  for persistence and for the broadcast; `redact_game_state` and `redact_event`
  run per recipient, and for a WebSocket per message (`app/events.rs`).
- **The creator alone sees an invited address.** `redact_game_state` clears
  `invited_email` for every other viewer.
- **A whole state in every message.** `GameEventDto` (`crates/api`) carries a
  complete `GameStateDto`, so a client that missed a message recovers from the
  next.
- **A freshness test on the client.** `should_apply_update`
  (`crates/ui/src/app.rs`) applies a state for a different game, or one with a
  strictly higher `version`, which stops an older HTTP response overwriting a
  newer WebSocket message.
- **The client already runs the rules.** `to_rules_board_state` and
  `to_rules_candidate` (`crates/ui/src/client_rules.rs`) let it validate and
  score a move before sending it.
- **The server sends data and the client formats it.** `ApiError` carries
  `blocking_games` as games, not as a sentence.
- **The token rides the WebSocket URL.** Browsers cannot set headers on the
  handshake (`websocket_url`, `crates/ui/src/app.rs`).

To move away from:

- **A hidden rack is an empty one.** `redact_game_state` replaces it with
  `RackDto { counts: [], blanks: 0 }`, which a client cannot tell from a seat
  with no tiles.
- **Access is one seat.** `ViewerAccess::Participant { seat_number }`, found
  with `.find(...)` in `resolve_viewer_access`, so a player with two seats sees
  one rack.
- **Conversions are server-only, and copied.** `board_from_dto`,
  `tile_from_dto` and `move_candidate_from_dto` (`game_state.rs`) return a
  `String` error; the UI has its own infallible `to_rules_*` set. No round-trip
  test compares the two ends.
- **Redaction and the seat's invitation are post-steps on a DTO.**
  `redact_game_state` and `attach_invitation_status` edit a built
  `GameStateDto`, so the DTO has no type that says what a recipient may see.
- **The envelope is three whole states.** `GameEventDto::{StateUpdated,
  GameStarted, GameFinished}` (tag `type`) carry no cause, no list of seats and
  no removal, and one broadcast channel carries every game, which each socket
  filters (`event_belongs_to_game`).
- **Prose in the data.** `MoveRecordDto.description` is a sentence built on
  the server.
- **An error has no code.** `ApiError` is `{ message, blocking_games }`.

## The model

The *wire* is the JSON the server and a client exchange. A *DTO* (data transfer
object) is a type that exists to be serialised for it. The *interface layer* is
a crate that depends on both the wire types and the domain and converts between
them, so that the server and every client built from Rust types hold the same
objects. The *view* a client holds, `GameView`, is the game as its viewer may
see it.

### DTOs are invisible

The requirement is an identity:

```text
state → DTO → state'        state' == state
```

Not "the conversion is careful" — an equality, testable as a property, over
`GameState`, `Rack`, `Tile`, `MoveCandidate` and the seat and game state
described in [`71-04-seats.md`](71-04-seats.md) and
[*The session*](71-03-version.md#the-session). It fails today for anything the
client cannot rebuild, which is how the gap went unnoticed: the server converts
one way, the client reconstructs what it can and does without the rest, and
nothing compares the two ends.

**Redaction has to be expressible in the model, not applied by blanking.** A
client does not receive the whole game: other players' racks and chat it may
not read are removed. So the identity holds over *what the recipient is
entitled to see*, and the objects have to be able to say "not visible" —
distinctly from "empty".

They cannot today: a hidden rack and a seat that has run out of tiles are the
same empty rack, to a client and to an engine reading the same object.

Two variants are enough, because how many tiles a seat holds is public:

```rust
pub enum SeatRack {
    Visible(Rack),   // your own seat, or the server's own view
    Hidden(u8),      // somebody else's — the count, which is public
}
```

An engine still gets what it needs: the board, its own rack, the rules. What it
must not get is a confident wrong answer about somebody else's.

**The count is UI work, not just a data fix.** How many tiles each opponent
holds is public information in this game and players use it — it is how you
know the bag is empty, who is about to go out, and whether an endgame is worth
blocking. The board currently cannot show it because the server does not send
it. Once it does, the seat list has somewhere to put it, and the change is
worth listing as its own piece of work rather than assumed to fall out of the
type: a number nobody displays is the same as no number.

**Access is a set of seats, not a tier.** `ViewerAccess` is currently
`Rejected | Creator | Participant { seat_number }`: a player holding two seats
sees one of their own racks and has the other hidden from them, which is a live
defect and the reason this has to be modelled rather than patched.

GAME-4 says a player may hold more than one seat, so what a viewer may see is
the union of what their seats may see, plus whether they created the game.
Creator stops being a rank below participant: somebody can be the creator and
hold two seats at once.

Three units, easily blurred and worth keeping apart. A *seat* plays: it holds
tiles, takes turns, is invited. An *account* is entitled: what may be seen is a
function of which seats it holds. A *connection* is addressed: it is where a
message is delivered. An account may have several connections and they all see
the same thing — a client is always an account, never a seat.

**One message per recipient, carrying every seat they hold.** Not one message
per seat: a player with two seats would otherwise receive the same board
twice. The message names which seat is on turn, so "your turn" is unambiguous
without being addressed seat by seat.

**What a viewer may see depends on who they are, not on whose turn it is.**
Showing only the on-turn seat's rack would make redaction depend on game
progress — the same state redacting differently as the turn moves — and would
protect nothing, since the holder sees each rack on its own turn and can
simply remember it. Entitlement is a function of identity; which rack to *show*
is the client's choice, and showing the seat about to play is the sensible
default.

In practice a person who wants to play twice registers two accounts and runs
two clients, which keeps the seats genuinely independent. The multi-seat path
exists chiefly because a bot account holds every seat its engine plays, and
humans inherit it rather than being expected to use it.

Somebody who does hold two seats gets view-switching without it being built:
each client chooses which seat to show, so two windows on one account can show
one seat each.

**The conversion lives in an interface layer.** Not in `api`, which depends on
`serde` alone and should not acquire the rules engine for everyone who wants a
wire shape; and not by collapsing wire and domain into one crate. A layer that
depends on both presents the same internal objects on each side, and the DTOs
are the bridge it hides.

The client environment is then an extension of the server environment rather
than a translation of it. The existing client already runs part of the rules
engine to validate and score a move before sending it; this makes that the
normal case rather than the exception, with the same objects reaching the same
code.

**Third-party clients are not served by this and should not be.** They convert
the wire format into whatever objects suit them, as any HTTP client would. The
interface layer is for clients that share the application's Rust types — which
is a smaller claim than "the DTOs are a public model", and a more honest one.

## serde and JSON

### The serde technology

serde is Rust's serialisation framework, and `serde_json` is its JSON format
([serde.rs](https://serde.rs/)):

- `#[derive(Serialize, Deserialize)]` generates the conversion from the type's
  own shape, so one definition gives both directions and they cannot disagree.
  A struct becomes a JSON object keyed by field name, a `Vec` an array and an
  `Option<T>` the value or `null`.
- Reading is forgiving in two ways. A missing `Option` field reads as `None`,
  and a field marked `#[serde(default)]` reads as its default, which is how a
  newer reader accepts an older snapshot. An unknown field is ignored unless
  the type says otherwise. `#[serde(skip_serializing_if = ...)]` leaves a field
  out of the output.
- An enum is *externally tagged* by default: `{"Hidden": {"count": 3}}`.
  `#[serde(tag = "kind")]` makes it *internally tagged*, the tag a field of the
  same object: `{"kind": "hidden", "count": 3}`. A unit variant is just the
  tag, `{"kind": "started"}`. A tuple variant cannot be internally tagged, so
  each variant is a struct or a unit. `#[serde(rename_all = "snake_case")]`
  renames the variants and fields in the output.
- A type that also derives `PartialEq` can be tested as a round trip:
  serialise, deserialise, compare.

### How the wire uses serde

`crates/api` derives both traits on every DTO and depends on nothing else;
`GameStateDto.version` already uses `#[serde(default)]` for a field added after
older snapshots existed. The enums the design adds are internally
tagged with `kind`, so a client in any language reads a variant by one field.
`GameView` itself is never serialised: `game_to_dto` and `game_from_dto` convert
it, and the identity in [*DTOs are invisible*](#dtos-are-invisible) is tested on
that pair. JSON is the one format, sent as the body of an HTTP response and as
a WebSocket text message.

## Cargo workspaces

### The Cargo workspace technology

Cargo builds Rust. A *package* is one `Cargo.toml` with a *crate*, a library or
a program, which is the unit of compilation
([The Cargo Book](https://doc.rust-lang.org/cargo/reference/workspaces.html)):

- A *workspace* is a root `Cargo.toml` listing member packages that share one
  `Cargo.lock`, one build directory and, through `[workspace.package]`, fields
  such as the version.
- A package depends on another by `path`, and the dependencies must form no
  cycle.
- A crate is compiled separately for each *target* a dependent is built for,
  from the same source. A dependency table may be limited to a target,
  `[target.'cfg(target_arch = "wasm32")'.dependencies]`, and a crate that a
  wasm32 build uses must itself compile for wasm32.

### How the wire uses the workspace

The root lists `members = ["crates/*", ...]`, so a new crate under `crates/` is
a member without an edit there. The browser client (`crates/ui`) builds for
wasm32 and the server for the host, so `game-wire` is one source compiled for
both, which is what lets the client rebuild the server's objects. The cycle rule
fixes the layering in [the interface layer](#the-interface-layer): `api` and
`rules-shared` know nothing of `game-wire`, which depends on both.

## HTTP and WebSocket with axum

### The axum technology

axum is the HTTP server framework on Tokio
([Tokio](71-03-version.md#the-tokio-technology);
[docs.rs](https://docs.rs/axum/latest/axum/)):

- A `Router` maps a path and a method to a handler, an `async fn`, such as
  `.route("/games/{game_id}/events", get(game_events))`.
- A handler's parameters are *extractors* that parse the request: `Path`,
  `Query`, `State` for shared state, `Json` for a body. Its return type
  implements `IntoResponse`, which is a status and a body.
  `.layer(...)` wraps the routes in middleware.
- A *WebSocket* starts as an HTTP request that is upgraded to a long-lived,
  two-way connection. The `WebSocketUpgrade` extractor takes it, and
  `on_upgrade` runs a task for the socket, which then sends and receives
  messages, a text message holding the JSON. Unlike a response, the server may
  send without a request.

### How the wire uses axum

A route handler returns a state as `Json(...)` and an error as a status with a
JSON body: today `ApiProblem` implements `IntoResponse` over `ApiError`
(`app/error.rs`), and `ErrorDto` takes its place. The WebSocket is
`/games/{game_id}/events`, upgraded in `game_events` and fed by `stream_events`
(`app/events.rs`); each message is `serde_json::to_string` of the envelope,
sent as text. A refused submission is an HTTP error, so the envelope has no
variant for it. The clients are `reqwest` and `tokio-tungstenite` natively and
`gloo-net` in the browser.

## The interface layer

A new crate. `api` keeps depending on `serde` alone; `rules-shared` keeps
knowing nothing about the wire.

```text
crates/api            DTOs and serde. No rules, no engine.
crates/rules-shared   the domain: GameState, Rack, Tile, MoveCandidate.
crates/game-wire      NEW. depends on both. GameView, GameMessage,
                      GameUpdate, GameLink, Bot and take_turn, and
                      GameView's conversion to and from the DTOs. Never
                      sees GameSession.
crates/server-game    depends on game-wire. Builds each GameView.
crates/ui             depends on game-wire.
crates/test-client    NEW. depends on game-wire.  (see 71-test-approach.md)
```

```rust
// crates/game-wire
pub fn game_to_dto(view: &GameView) -> GameStateDto;
pub fn game_from_dto(dto: &GameStateDto) -> Result<GameView, WireError>;

pub fn board_from_dto(cells: &[BoardCellDto], alphabet: &Alphabet)
    -> Result<BoardState, WireError>;
pub fn tile_from_dto(tile: TileDto, alphabet: &Alphabet)
    -> Result<Tile, WireError>;
pub fn rack_from_dto(rack: &RackDto) -> Rack;
pub fn move_candidate_from_dto(candidate: MoveCandidateDto,
    rules: &VariantRules) -> Result<MoveCandidate, WireError>;
```

The board, tile, rack and move-candidate conversions replace two sets of copies:
`board_from_dto`, `tile_from_dto` and `move_candidate_from_dto` in `server-game`
(`game_state.rs`), which return a `String` error, and `to_rules_tile`,
`to_rules_candidate`, `to_rules_board_state` and `to_rules_rack` in the UI
(`crates/ui/src/client_rules.rs`). The `game-wire` functions return `WireError`.

**`GameView` is what a client can rebuild** — the game as this viewer is
entitled to see it, with `SeatRack::Hidden` where a rack was withheld. It is
not `GameSession`: a client has no bag and no other player's tiles, and a type
that pretended otherwise would be lying in the type system. The type is
defined in `game-wire`, because the server builds it and every client reads it.
It carries its game's id, so a client holding several games reads which one a
view is of from the view.

**The server builds the `GameView`; `game-wire` only converts it.**
`GameSession::view_for` lives in `server-game` (`game_state.rs`), where the
bag and every rack are:

```rust
// crates/server-game
impl GameSession {
    pub fn view_for(&self, viewer: &ViewerAccess, players: &PlayerLookup) -> GameView;
}
```

`PlayerLookup` holds the display name and rating of each player in the game. The
caller passes it in, because user details are always a lookup and never copied
into game data ([*Open questions*](71-09-open-questions.md#open-questions)): the
handlers, the Roster, the Invitations, the admin routes and the Event stream
each read the names from Accounts and the ratings from Ratings, then call
`view_for`, then `game_to_dto`. `GameView` is one type, so the server's code and
a client's, `take_turn` included, read the same thing.[^layers]

**The identity is a property test in `game-wire`**, stated over `GameView`:

```rust
// for any view:
game_from_dto(&game_to_dto(&view))  ==  Ok(view)
```

What a viewer may see is proved where `view_for` is, in `server-game`: a viewer
holding two seats sees both racks, and every other rack is `Hidden`.

**The client core** is the one interface every client sits on, and it is in
`game-wire` too. `game-wire` defines what crosses it as two enums, one for each
direction:

```rust
// crates/game-wire
/// To the server: a move, pass, exchange, resign and the rest. The variants
/// are in 71-03-version.md, "One version, moved in one place".
pub enum GameMessage { /* ... */ }

/// From the server: what a subscriber is told.
pub enum GameUpdate {
    /// A game's new state, and the event that produced it. `because` is
    /// absent on the first yield (the current view on join) and when the
    /// receiver has skipped states (71-06-engine.md, How the Event stream uses watch).
    Game { view: GameView, because: Option<GameEventDto> },
    /// The account's new list of seats, one entry for each seat it holds.
    Seats(Vec<SeatRef>),
    /// A game no longer exists; nothing more follows for it.
    GameRemoved(GameId),
}

/// One seat of one game. A list of these, not of games, lets one bot hold
/// several seats in a game.
pub struct SeatRef { pub game_id: GameId, pub seat: u8 }
```

`GameUpdate` is a proposed name. `GameEventDto`
([*Structured descriptions*](71-05b-wire-types.md#structured-descriptions))
holds seat numbers, player ids, words, scores and counts, nothing hidden from
any player, so it is safe for any recipient; the server keeps its own
`GameEvent` and converts it to `GameEventDto` once, when it publishes. A link
moves only these two enums. The client core has two calls, and no server type in
either:

```rust
pub trait GameLink {
    /// The next update in this subscription's scope. A GameView carries its
    /// game's id. Scope is what the transport subscribed to. A bot object's
    /// link is scoped to its seat's game: in-process, its bot's task feeds it
    /// (71-06-engine.md, The model); externally, it is one game's WebSocket. An external harness may
    /// also subscribe to every seated game (71-06-engine.md, How the Event stream uses watch). The web client: one game.
    async fn on_event(&mut self) -> Result<GameUpdate, LinkError>;
    /// Send a message for a game; the answer is the server's, accepted or
    /// refused.
    async fn submit(&self, game_id: GameId, message: GameMessage)
        -> Result<(), SubmitError>;
}
```

The web client, the test client, an external harness and the in-process bot each
call these two, and see only the two enums. A transport is an adapter behind
them ([the model](71-06-engine.md#the-model)).

**`GameLink` is a trait with two implementations, chosen at compile time.**
`Bot<L: GameLink>`, with `take_turn`, is in `game-wire`, where the server and
the harness of #10 share it
([the generic type](71-06-engine.md#the-generic-type-technology)). The
implementations are `InProcessLink`, which stays in `server-game` with the glue
and hands the enums over as Rust values, and `ExternalLink` (the name is
proposed), which turns them into JSON and back over HTTPS and the WebSocket,
through the DTOs and `game_to_dto` and `game_from_dto`. The server builds
`Bot<InProcessLink>` and a harness builds `Bot<ExternalLink>`. The web client
uses `ExternalLink` with a one-game scope and builds no `Bot`.

**Sign-in belongs to the link.** An `ExternalLink` is built by signing in and
keeps the token; an `InProcessLink` is built with the listed bot's identity.
`Bot<L>` never signs in, so it is the same code on a client and in the
server.[^watch]

[^layers]: Owner, 2026-10-20: `game-wire` converts `GameView` both ways and
    never sees `GameSession`; the server builds the view. A bot harness
    behaves like the existing client, over the internet or in-process.

[^watch]: Owner, 2026-10-20: the per-game channel is a `watch`, the account's
    seats are a `watch`, one bot holds several seats, one bot per strength,
    sign-in belongs to the link, one task per subscriber, and `game-wire`
    defines `GameMessage` and `GameUpdate`.
