# 3.2.4 Dark Portal's workstreams

Dark Portal's workstream register. What a workstream is, and the generic
workstreams, are [1.3](../../docs/1.3-workstreams.md); the form is
[the template](../../docs/templates/workstream-register.md). The code does not
exist yet, so each workstream names what it will own; paths, and each
workstream's artefacts table, follow with the code. Client, Operations &
Infrastructure, Delivery Tooling and Capacity & Performance have no section of
their own until a boundary needs one.

## This application's workstreams

| Workstream | Instance of | Owns |
| --- | --- | --- |
| DP: Application Architecture | Application Architecture | the Blizzard API client, the hourly auction snapshots, game data (items, recipes, professions), the stored data and its model |
| DP: Market Analysis | a domain workstream | prices, crafting margins with flipping included (buying an item to resell it, a recipe whose input and output are the same item), risk indicators and trading strategies |
| DP: Client | Client | what the owner sees and types: the command-line tool and the notebook, and any later GUI |
| Operations & Infrastructure | the same | the running collector, watched and recovered, and the Blizzard API credentials; the host is [Infrastructure's](../infrastructure/README.md) |
| DP: Delivery Tooling | Delivery Tooling | this application's machinery from a commit to a running environment |
| Capacity & Performance | the same | whether Dark Portal's memory, its Blizzard API quota and its storage growth will still fit, and how fast the analysis runs |

Dark Portal's own `Workstream` options carry the prefix `DP:`,
by [1.3 *How the names are written*](../../docs/1.3-workstreams.md#how-the-names-are-written).

The generic workstreams with no instance here:

| Workstream | Why |
| --- | --- |
| Security & Access | the owner is the only user and reaches the service privately ([489 design](../infrastructure/3.3.7-changes/489-shared-infrastructure/489-design.md#how-dark-portal-is-reached-privately)), so there are no accounts to manage |
| Client Distribution | nothing is distributed yet: the notebook comes first, on the owner's machine, then the command-line tool on the server ([dp#3](https://github.com/delphside/dark-portal/issues/3)); getting the notebook and its data to the owner's machine is part of [dp#5](https://github.com/delphside/dark-portal/issues/5), first in its stage 1 package [dp#7](https://github.com/delphside/dark-portal/issues/7) |
| Process Definition and Programme Tooling | they manage the programme itself, and are in [2.6](../../records/2.6-workstreams.md) |

### Application Architecture

Getting the market and game data in, and keeping it in a shape the analysis can
use. It is one capability because what is collected, how often and how it is
stored are decided together.

#### Application Architecture and Market Analysis

| Subject | Owner |
| --- | --- |
| a snapshot, an item, a recipe as data: what is stored and for how long | DP: Application Architecture |
| the transforms from bronze (the source snapshots) to silver and gold, the inferred events included | DP: Application Architecture, built in [dp#5](https://github.com/delphside/dark-portal/issues/5), the first version in [dp#7](https://github.com/delphside/dark-portal/issues/7) |
| what a price, margin or risk means and how it is worked out | DP: Market Analysis |

### Market Analysis

Turning prices into decisions: current price and history, crafting margins,
risk and the strategies built on them. A domain workstream because it has
mechanisms of its own (pricing, margins, risk and strategies) and changes with
how the owner trades, not with how data arrives.
