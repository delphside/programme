# 1.10 Development standards

The development standard: how the code of every application, and of the
programme's own tooling, is built. It covers where code goes, how settings
and the identifiers the tooling writes are held, what a script's exit status
means, how code is commented and what each language is written to. Each
application's development document holds its own toolchain and commands: Tile
Lite Elite's is
[4.3.2](https://github.com/delphside/tile-lite-elite/blob/main/docs/4.3.2-development.md).
How the documents are written is [1.5](1.5-writing-documents.md), and how the
code is tested is [1.9](1.9-testing-standards.md).

Each language's rules start from a published standard, named in
[*Each language starts from its standard*](#each-language-starts-from-its-standard).
Where this page is silent, that standard applies; where the two differ, this
page wins.

## Where code goes

- **A rule is implemented in one place**: where the application's design map
  says it lives (Tile Lite Elite's is
  [4.2.0](https://github.com/delphside/tile-lite-elite/blob/main/docs/4.2.0-design-map.md)),
  or for the programme's tooling where [1.1](1.1-programme-tooling.md)'s
  tables say. A change that moves a rule removes the copies it leaves.
- **The board is read through one model**, `scripts/board/` in the programme
  repository. A script that needs the board extends the model rather than
  reading GitHub a second way.

## Where an application's settings are held

Every setting is listed in the application's configuration reference,
(3+n).4.1 ([1.5](1.5-writing-documents.md#where-an-applications-settings-are-listed)).
Two kinds are held differently, following the Twelve-Factor App's
[*Config*](https://12factor.net/config) factor, which separates what varies
between deploys from what does not:

| Kind | For example | Held in |
| --- | --- | --- |
| deployment setting | addresses, keys, hosts | environment variables, set per environment |
| product setting | notification defaults, rate limits, retention periods, time limits | one code module per area, so a change is made in one place and the compiler checks it |

## A string stored outside the repository is an identifier

A string the tooling writes into GitHub (a marker in an issue body, a field or
option name, a label) is an identifier, not text to keep current. Renaming it
in the code makes the tooling blind to every copy already written, so it is
never changed as part of a rename or a move. One that must change is a
decision, and the change migrates the copies.
[1.6](1.6-github-project-board.md#what-the-tooling-reads-and-would-break-on)
lists the strings the tooling reads.

## What a script's exit status means

Severity only. A wait status carries eight bits, so it cannot carry an
identifier: `exit 256` is observed as `0`. Scripts and scheduled jobs report
through the application's documented log events, not through a numeric code
scheme. What a failure must tell its reader is a design question
([1.2 §2.13](1.2-change-lifecycle.md#and-what-it-reports-when-it-goes-wrong)).

| Exit | Means |
| --- | --- |
| `0` | it worked. Information and warnings still exit `0` |
| `1` | fatal: it went wrong and the run stopped. Nothing reached users |
| `2` | could not judge: the check could not run, for want of a tool, a network or an argument. A check uses it so a missing tool cannot read as a pass |
| `3` | non-fatal: it went wrong and the run continued. A deploy returns it when production is live and a step after the swap failed |

## Comments in code

Rust doc comments follow the documentation chapter of the
[Rust API Guidelines](https://rust-lang.github.io/api-guidelines/documentation.html),
and are written as the
[rustdoc book](https://doc.rust-lang.org/rustdoc/how-to-write-documentation.html)
describes. The standard library is the model to copy, at less length. Two of
the guidelines, `C-METADATA` and `C-RELNOTES`, do not apply: they are for
crates published to crates.io, and the programme's crates are unpublished.

Five house rules go with the guidelines:

- **Every public item has a doc comment.** An item that is public
  only as plumbing is made private, or hidden (`C-HIDDEN`), and carries no doc
  comment.
- **An example is given where it shows something the signature does not**,
  applying `C-EXAMPLE` "within reason": the crates have no outside users, and
  an example is compiled and run as a test.
- **A doc comment names the rule it enforces, by its ID in the application's
  rules** (Tile Lite Elite's `docs/4.1.0`), so the code, the rules, the design
  documents and the test design point at each other.
- **A doc comment says what else the item changes**: what it persists or
  broadcasts and which state transition it makes.
- **A doc comment links to the numbered document that owns a fact**, in place
  of the fact.

Inline comments, `//` in Rust and `#` in Python and shell, in every repository
of the programme:

- **An inline comment says why a line is as it is**, where the code cannot.
- **The history of a decision goes in the commit and the issue**, as for
  documents.
- **The failure a guard exists to prevent is kept beside the guard**, the
  exception to the line above
  ([1.5 *Keep the evidence, not the argument*](1.5-writing-documents.md#keep-the-evidence-not-the-argument)).
- **Future work goes in an issue.**

Tile Lite Elite's comment inventory, `scripts/measure/comment-inventory.py`,
lists the comment blocks of its delivery scripts, `deploy.sh` and `verify.sh`,
that cite an issue or a date; the dated ones are its regression list.

## The toolchain is pinned, and CI checks its style

- **The compiler or interpreter version is pinned in a file in the
  repository**, so CI, the release build and a developer's machine build with
  the same one, and a bump is a commit. Tile Lite Elite's is
  `rust-toolchain.toml`.
- **The language's formatter and linter run in CI, and a warning fails the
  build.** Tile Lite Elite's `check` job runs `cargo fmt --check` and `clippy
  -D warnings`
  ([4.3.3 §2.3](https://github.com/delphside/tile-lite-elite/blob/main/docs/4.3.3-testing-ci-and-release.md#23-continuous-integration)).

## Each language starts from its standard

| Language | Standard | House rules |
| --- | --- | --- |
| Rust | the [Rust API Guidelines](https://rust-lang.github.io/api-guidelines/), formatted by `rustfmt`'s default style | lint with Clippy's default set |
| Python | [PEP 8](https://peps.python.org/pep-0008/) | the standard library only, so a script runs on a bare CI runner and in a fresh cloud session with nothing to install |
| shell | the [Google Shell Style Guide](https://google.github.io/styleguide/shellguide.html) | Bash, and `set -euo pipefail` at the top, except a script that must go on past a failure, which says why beside the line: a Claude Code hook must never stop the session it serves |
