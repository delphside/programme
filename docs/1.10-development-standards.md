# 1.10 Development standards

The development standard: how the code of every application, and of the
programme's own tooling, is built. It covers where a rule is implemented, how
settings and the identifiers the tooling writes are held, the one scheme every
error and exit status follows, how code is commented, and each language's
standard, pinned toolchain and checks. The technical lead
([1.7](1.7-roles-and-responsibilities.md#technical-lead)) builds to it, and the
`change-reviewer` agent reviews against it. Each application's development
documents hold its own toolchain and commands: Tile Lite Elite's are
[4.3.1](https://github.com/delphside/tile-lite-elite/blob/main/docs/4.3.1-setup.md)
to
[4.3.3](https://github.com/delphside/tile-lite-elite/blob/main/docs/4.3.3-testing-ci-and-release.md).
How the documents are written is [1.5](1.5-writing-documents.md), and how the
code is tested is [1.9](1.9-testing-standards.md).

Where a language has a published standard, named in
[*Each language's standard and checks*](#each-languages-standard-and-checks),
it applies where this page is silent; where the two differ, this page wins.

## One place for each rule

- **A rule is implemented in one place**: where the application's design map
  says it lives (Tile Lite Elite's is
  [4.2.0](https://github.com/delphside/tile-lite-elite/blob/main/docs/4.2.0-design-map.md)),
  or for the programme's tooling where [1.1](1.1-programme-tooling.md)'s
  tables say. A change that moves a rule removes the copies it leaves.
- **The board is read through one model**, `scripts/board/` in the programme
  repository. A script that needs the board extends the model.

## Where an application's settings are held

The settings are listed as
[1.5](1.5-writing-documents.md#where-an-applications-settings-are-listed) says.
Two kinds are held differently, following the Twelve-Factor App's
[*Config*](https://12factor.net/config) factor, which separates what varies
between deploys from what does not:

| Kind | For example | Held in |
| --- | --- | --- |
| deployment setting | addresses, keys, hosts | environment variables, set per environment |
| product setting | notification defaults, rate limits, retention periods, time limits | one code module per area |

A product setting in one module is changed in one place, and the build checks
it.

## A string stored outside the repository is an identifier

A string the tooling writes into GitHub or matches there (a marker in an issue
body, a field or option name, a label) is an *identifier*, not text to keep
current. Renaming it in the code makes the tooling blind to every copy already
written, so it is never changed as part of a rename or a move. Changing one is
a change of its own, and it migrates every copy.
[1.6](1.6-github-project-board.md#what-the-tooling-reads-and-would-break-on)
lists the strings and routes a change to one.

## Errors: one scheme for every system

**Every error has a type and a severity.** The type says whose problem it is
and what to do about it; the severity says what happened to the run. The
scheme covers every application's API, every script and tool, and what comes
back from a vendor such as Oracle or GitHub. Its terms are HTTP's
status classes ([RFC 9110](https://www.rfc-editor.org/rfc/rfc9110#section-15)),
gRPC's [status codes](https://github.com/grpc/grpc/blob/master/doc/statuscodes.md)
as Google's [AIP-193](https://google.aip.dev/193) maps them, OpenTelemetry's
[log severities](https://opentelemetry.io/docs/specs/otel/logs/data-model/),
BSD's
[`sysexits.h`](https://github.com/freebsd/freebsd-src/blob/main/include/sysexits.h)
and the saga pattern. Code takes the scheme when its errors next change.

### The type of an error

| Type | What it is | HTTP served | A dependency's answer | Retried | Who acts |
| --- | --- | --- | --- | --- | --- |
| *business* | the request is wrong, a rule refuses it, or the thing is correctly not there | 400, 403 for the application's own rule, 404, 409, 422 | a not-found for something the user named; 409 | never | the user fixes the input |
| *technical*, *blip* | the service or the network failed for now | 503 with `Retry-After` | 429, 502, 503, 504, a vendor's quota, a timeout, a lost connection | yes, with backoff, honouring `Retry-After`, in the adapter's bottom layer | nobody, unless it keeps failing |
| *technical*, *fundamental* | a credential, a right, a setting, a tool or a local resource is missing or wrong | 401 | a second 401; a platform's policy 403; a 404 for an identifier from the system's own settings; a missing tool; a missing or malformed setting; a full disk; exhausted memory | never | the operator |
| *unexpected* | any error the code did not expect, such as a defect in the code or a vendor's | 500 | 500; a 4xx the system's own call caused; a reply the code cannot use | never | whoever raises an issue; the log keeps the cause |

- **401 means only "no valid credential".** A refusal by the system's own rule
  is 403, *business*. A client holding a token refreshes it once on a 401; only
  a second 401 is *fundamental*.
- **A 429 a system serves is the caller's doing**: the caller retries it as a
  blip, and the log counts it apart from a capacity 503.
- **A 404 is *business* only for a thing the user named.** For an identifier
  from the system's own settings it is *fundamental*.

**An adapter to an external system has three layers**, and each meets its own
errors:

- **The bottom layer calls one vendor API.** It meets the technical errors
  (authorisation, the network, timeouts, output not in the expected form) and
  retries the blips.
- **The middle layer offers one typed function per vendor operation.** It
  always makes a well-formed call, and turns the vendor's answer, a refusal or
  an invalid reply included, into one of the types in the table.
- **The top layer is the port, in the application's own terms.** It validates
  the request and wraps the errors from the layers beneath it.

### The severity of an error

Severity belongs to a run: a script, a job or one request. Only *fatal* and
*error* carry a type; a blip that a retry cleared is a *warning* with none.

| Severity | What happened to the run | Log level |
| --- | --- | --- |
| *fatal* | it stopped and the work is not done | `FATAL` |
| *error* | something failed, the run carried on, and the rest of the work is done | `ERROR` |
| *warning* | nothing failed, but it is for a person to look at: a retry that succeeded, no new data, a valid but implausible payload | `WARN` |
| *info* | it happened, for the record | `INFO` |

A failed request is *fatal* to that request and carries its type. The server
itself carries on, so it logs the failure at `ERROR` for an unexpected error,
`WARN` for a technical one and `INFO` for a business one.

### What a script's exit status means

**An exit status says first whether the run completed, then why it stopped.**
A script documents its statuses in its header and `--help`
([1.2 §2.13](1.2-change-lifecycle.md#and-what-it-reports-when-it-goes-wrong)).
A status carries eight bits, so a value above 255 wraps: `exit 256` is observed
as `0`.

| Exit | Means |
| --- | --- |
| `0` | completed, with at most warnings and information |
| `3` | completed with errors: the run carried on past one or more failures, each logged with its type |
| `1` | stopped on a *business* error; from a command that answers a question, the answer *no* |
| `2` | stopped on a *technical, fundamental* error |
| `75` | stopped on a *technical, blip* that kept failing (`EX_TEMPFAIL`); a later retry may work |
| `70` | stopped on an *unexpected* error (`EX_SOFTWARE`) |
| `64` | stopped on a usage error: a bad flag or a missing argument (`EX_USAGE`) |
| `65` | from a command that answers a question, stopped on a *business* error (`EX_DATAERR`) |
| `130` | interrupted; the message says whether the change is live and names the rerun |

- **A command that answers a question exits `0` for *yes* and `1` for *no***,
  as `grep` does: a query's *no*, a gate's refusal, a confirmation the operator
  declines, and a check's findings when it runs as a gate (with `--exit-code`,
  or wherever its caller stops on them). None is an error. Its business errors
  exit `65`, so a misspelt argument can never be read as *no*. A check that
  could not judge exits `2` or `75`. A check run to report, for a person to
  read, exits `0` and logs its findings as warnings.
- **A hook's "not yet" exits `75`**, since its remedy is a blip's: try later.
- **A dry run exits as the real run would** where it stops, and never `3`.
- **A run killed by a signal** (128 + n, such as an out-of-memory kill's 137)
  is read as *unexpected*. A script maps every status a child returns, such as
  ssh's 255, to this table.
- **A scheduler retries on `75` alone** and pages on `70`.

### When an error stops the run

**Each script that changes something names its *pivot***, the step after which
its change is live: the term of the
[saga pattern](https://learn.microsoft.com/en-us/azure/architecture/patterns/saga),
in which steps before it are compensable and steps after it retryable. A pivot
belongs to a unit of work, so a run over several images or sources has one for
each, and the script's header names it.

- **Before the pivot, every error is fatal.** The run undoes what it changed,
  and every host-changing step before the pivot is inside that undo. It exits
  by the error's type. If the undo fails too, the message names the state left
  and the command that repairs it.
- **After the pivot, an error is an *error*.** The run logs it, carries on
  with the remaining steps, and exits `3`. Each step after the pivot is safe to
  rerun, and the message names the command that reruns it. A failed check of
  the live change names the rollback.
- **In bash, the steps after the pivot run without `errexit`** or through a
  checked wrapper, with a test that proves a failure there does not end the
  run.
- **A job capturing data that cannot be fetched again keeps its raw input
  before the pivot.** Where its retry window closes for good, running out of
  it is *fatal*, exit `75`, and the gap is recorded as data.

### Rules for every system

- **A dependency's answer is translated, never passed through.** An adapter's
  middle layer turns a vendor's answer into one of these types; a vendor's 400
  means the system's own call was wrong, so it is *unexpected*. A GraphQL answer
  carrying both data and errors is an *error*, never silently partial.
- **A back-end error is wrapped in the system's own result**, with the vendor's
  answer as its `cause`. A message names what happened and the next step, never
  a stack trace or a vendor's words.
- **An answer kept vague for security wins over a precise reason**: every
  failed sign-in gives the same message.
- **An unexpected error, a panic included, answers 500**, never a dropped
  connection, which a client would retry as a blip.
- **Every response is a result**, a framework's rejection and a refused
  WebSocket upgrade included. A live WebSocket that fails closes with code
  4000 plus the HTTP status it stands for.
- **New HTTP APIs answer errors as
  [RFC 9457](https://www.rfc-editor.org/rfc/rfc9457) Problem Details.** An API
  moving to it keeps its old fields beside the new ones for at least one
  release.

### The result object

Every run, call and request ends in one result object, success included. Its
`reason`, `domain` and `metadata` follow AIP-193's `ErrorInfo`, and its
`violations` AIP-193's `BadRequest`. A result's `outcome` is its severity, with
`ok` for *info*. It serialises as Problem Details over
HTTP, where `cause` and `errors` are left out for a caller outside the
programme.

| Field | Holds |
| --- | --- |
| `outcome` | `ok`, `warning`, `error` or `fatal`, as this result reports it |
| `type` | for `error` and `fatal`: `business`, `technical` or `unexpected` |
| `blip` | for a technical error: `true` for a blip, `false` for a fundamental error |
| `reason` | a stable code in UPPER\_SNAKE\_CASE, unique in its domain and never reused |
| `domain` | the system that names the reason: for example the board tooling's `board`, or `oracle` in a cause from Oracle |
| `message` | one sentence for the user: what happened and the next step; in the programme's own results, no vendor text, address or identifier |
| `metadata` | the operation's context, by key |
| `violations` | for a refused input, one entry per value at fault: `field`, `value`, `limit` and `reason` |
| `cause` | the result from the layer or system below; so the object is recursive |
| `errors` | the results of the failures a run carried on past, one per unit of work |

The outcome is the reporter's: the same back-end error is `fatal` before a
pivot and `error` after it, and a `cause` keeps the outcome it had where it
happened. In logs the fields take the `error.` prefix of OpenTelemetry's
`error.type` attribute: `error.type`, `error.reason` and `error.domain`.

In Python, `Result` is a frozen dataclass, and a failure is raised as
`ProgrammeError`, with a subclass per type, `BusinessError`, `TechnicalError`
and `UnexpectedError`, carrying its result; the cause is chained with
`raise … from`. A tool holds them in one module, shared by its scripts, and
maps an exception to its exit status in one place. In Rust the type takes
another name, such as `Report`, since `Result` is the standard library's.

### Examples

The first nine are Turpin's and the board tooling's, the last two Tile Lite
Elite's.

| What happens | Type | Outcome | Exit or HTTP |
| --- | --- | --- | --- |
| a deploy is asked for a version never released | *business* | `fatal`, before any change | `1` |
| a registry copy gets 503 twice, then succeeds | none: a retry cleared the blip | `warning` | `0` |
| a registry copy gets 503 on every try | *technical*, *blip* | `fatal` | `75` |
| a revoked API key gets 401 | *technical*, *fundamental* | `fatal` | `2` |
| one delete of six is refused by a policy | *technical*, *fundamental* | `error`: five are removed | `3` |
| the registry returns a manifest the code cannot read | *unexpected* | `fatal` | `70` |
| the deploy is live, then settling the milestone fails | *technical*, *blip* | `error`: the deploy stands | `3` |
| a hook asks a query about a misspelt SHA | *business* | `fatal` | `65`, never read as *no* |
| a query's answer is *no* | none: an answer | `ok` | `1` |
| a player plays a word not in the dictionary | *business* | `fatal` to the request; logged at `INFO` | HTTP `400` |
| a database query fails inside the server | *unexpected* | `fatal` to the request; logged at `ERROR` | HTTP `500` |

## Comments in code

Rust doc comments follow the documentation chapter of the
[Rust API Guidelines](https://rust-lang.github.io/api-guidelines/documentation.html),
and are written as the
[rustdoc book](https://doc.rust-lang.org/rustdoc/how-to-write-documentation.html)
describes. The standard library is the model to copy, at less length. Two of
the guidelines, `C-METADATA` and `C-RELNOTES`, do not apply: they are for
crates published to crates.io, and the programme's crates are unpublished.

Five house rules for doc comments, which are Rust's, go with the guidelines:

- **Every public item has a doc comment.** An item that is public
  only as plumbing is made private, or hidden (`C-HIDDEN`), and carries no doc
  comment.
- **An example is given where it shows something the signature does not**,
  applying `C-EXAMPLE` "within reason": the crates have no outside users, and
  an example in a library crate is compiled and run as a test.
- **A doc comment names the rule it enforces, by its ID in the application's
  rules** (Tile Lite Elite's `docs/4.1.0`), so the code, the rules, the design
  documents and the test design point at each other.
- **A doc comment says what else the item changes**: what it persists or
  broadcasts and which state transition it makes.
- **A doc comment links to the numbered document that owns a fact**, in place
  of the fact.

Inline comments, in every language and repository of the programme:

- **An inline comment says why a line is as it is**, where the code cannot.
- **The history of a decision goes in the commit and the issue**, as for
  documents.
- **The failure a guard exists to prevent is kept beside the guard**, the
  exception to the history rule
  ([1.5 *Keep the evidence, not the argument*](1.5-writing-documents.md#keep-the-evidence-not-the-argument)).
- **Future work goes in an issue.**

## Each language's standard and checks

| Language | Standard | Version pinned by | CI checks | House rules |
| --- | --- | --- | --- | --- |
| Rust | the [Rust API Guidelines](https://rust-lang.github.io/api-guidelines/) | a toolchain file in the repository: Tile Lite Elite's `rust-toolchain.toml` | `rustfmt` in its default style and Clippy's default lints, a warning failing the build | the [doc-comment rules](#comments-in-code) |
| Python | [PEP 8](https://peps.python.org/pep-0008/) | nothing: CI's runner image | none | the standard library only |
| shell | the [Google Shell Style Guide](https://google.github.io/styleguide/shellguide.html) | nothing | none | Bash, under `set -euo pipefail` |

The inline-comment rules of [*Comments in code*](#comments-in-code) apply to
every language; the doc-comment rules are Rust's. Review is the only check of
Python and shell against their standards. Other files (TypeScript, JavaScript,
SQL, awk, bats, HTML, CSS, YAML) have no standard named here.

**Pinning a version in the repository** makes CI, the release build and a
developer's machine build with the same one, and makes a bump a commit.

**Python uses the standard library only**, so a script runs on a bare CI
runner and in a fresh cloud session with nothing to install.

**A shell script runs under `set -euo pipefail`**, set at its top or by a
shared library it sources first (Dark Portal's `sizing/lib.sh`). Four kinds
are excepted:

- a hook that cannot refuse (a Claude Code hook, or a git hook such as
  `post-merge`) and a session's setup script, which must never stop the
  session or command they serve: each leaves out `-e`, or the whole `set`
  line, and says why in its header;
- a check that runs every step and reports all its failures (the programme's
  `check-docs.sh`, Tile Lite Elite's `verify.sh`): it runs under
  `set -uo pipefail` and says why in its header;
- a wrapper that only sources a shim or `exec`s another script, and the shim
  it sources;
- a library sourced by scripts that set their own options, which runs under
  theirs.

A hook that refuses, such as `pre-commit`, is under the main rule.
