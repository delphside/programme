# 1.10 Development standards

The development standard: how the code of every application, and of the
programme's own tooling, is built. It covers where a rule is implemented, how
settings and the identifiers the tooling writes are held, what a script's exit
status means, how code is commented, and each language's standard, pinned
toolchain and checks. The technical lead
([1.7](1.7-roles-and-responsibilities.md#technical-lead)) builds to it, and the
`change-reviewer` agent reviews against it. Each application's development
documents hold its own toolchain and commands: Tile Lite Elite's are
[4.3.1](https://github.com/delphside/tile-lite-elite/blob/main/docs/4.3.1-setup.md)
to
[4.3.3](https://github.com/delphside/tile-lite-elite/blob/main/docs/4.3.3-testing-ci-and-release.md).
How the documents are written is [1.5](1.5-writing-documents.md), and how the
code is tested is [1.9](1.9-testing-standards.md).

Where a language has a published standard, named in
[*Each language's standard and checks*](#each-languages-standard-and-checks),
it applies where this page is silent; where the two differ, this page wins.

## One place for each rule

- **A rule is implemented in one place**: where the application's design map
  says it lives (Tile Lite Elite's is
  [4.2.0](https://github.com/delphside/tile-lite-elite/blob/main/docs/4.2.0-design-map.md)),
  or for the programme's tooling where [1.1](1.1-programme-tooling.md)'s
  tables say. A change that moves a rule removes the copies it leaves.
- **The board is read through one model**, `scripts/board/` in the programme
  repository. A script that needs the board extends the model.

## Where an application's settings are held

The settings are listed as
[1.5](1.5-writing-documents.md#where-an-applications-settings-are-listed) says.
Two kinds are held differently, following the Twelve-Factor App's
[*Config*](https://12factor.net/config) factor, which separates what varies
between deploys from what does not:

| Kind | For example | Held in |
| --- | --- | --- |
| deployment setting | addresses, keys, hosts | environment variables, set per environment |
| product setting | notification defaults, rate limits, retention periods, time limits | one code module per area |

A product setting in one module is changed in one place, and the build checks
it.

## A string stored outside the repository is an identifier

A string the tooling writes into GitHub or matches there (a marker in an issue
body, a field or option name, a label) is an *identifier*, not text to keep
current. Renaming it in the code makes the tooling blind to every copy already
written, so it is never changed as part of a rename or a move. Changing one is
a change of its own, routed as
[1.6](1.6-github-project-board.md#what-the-tooling-reads-and-would-break-on)
says, and it migrates every copy.

## What a script's exit status means

**An exit status says how a run ended**, as the table below says. A script's
exit status carries eight bits, so a value above 255 wraps: `exit 256` is
observed as `0`. A script reports what went wrong in its exit status and
documents it in its header and `--help`
([1.2 §2.13](1.2-change-lifecycle.md#and-what-it-reports-when-it-goes-wrong)).

| Exit | Means |
| --- | --- |
| `0` | It worked. Information and warnings still exit `0`. |
| `1` | Fatal: it went wrong and the run stopped. A query that answers "no" also exits `1`, and some scripts use it for a read that could not be made or a run that did only part of its work (for example `board-release.py`, `board-add.py` and `board-stage.py`). |
| `2` | Could not judge: the check could not run, for want of a tool, a network or an argument. A check uses it so a missing tool cannot read as a pass. |
| `3` | Non-fatal: it went wrong and the run continued. A deploy returns it when the new version is live in production and a later step failed. |
| `70` | A crash or a profile error in the programme's board tooling (`profile.run`), so a caller can tell it from a query's `1`. |

## Comments in code

Rust doc comments follow the documentation chapter of the
[Rust API Guidelines](https://rust-lang.github.io/api-guidelines/documentation.html),
and are written as the
[rustdoc book](https://doc.rust-lang.org/rustdoc/how-to-write-documentation.html)
describes. The standard library is the model to copy, at less length. Two of
the guidelines, `C-METADATA` and `C-RELNOTES`, do not apply: they are for
crates published to crates.io, and the programme's crates are unpublished.

Five house rules go with the guidelines:

- **Every public item has a doc comment.** An item that is public
  only as plumbing is made private, or hidden (`C-HIDDEN`), and carries no doc
  comment.
- **An example is given where it shows something the signature does not**,
  applying `C-EXAMPLE` "within reason": the crates have no outside users, and
  an example in a library crate is compiled and run as a test.
- **A doc comment names the rule it enforces, by its ID in the application's
  rules** (Tile Lite Elite's `docs/4.1.0`), so the code, the rules, the design
  documents and the test design point at each other.
- **A doc comment says what else the item changes**: what it persists or
  broadcasts and which state transition it makes.
- **A doc comment links to the numbered document that owns a fact**, in place
  of the fact.

Inline comments, in every language and repository of the programme:

- **An inline comment says why a line is as it is**, where the code cannot.
- **The history of a decision goes in the commit and the issue**, as for
  documents.
- **The failure a guard exists to prevent is kept beside the guard**, the
  exception to the history rule
  ([1.5 *Keep the evidence, not the argument*](1.5-writing-documents.md#keep-the-evidence-not-the-argument)).
- **Future work goes in an issue.**

## Each language's standard and checks

| Language | Standard | Version pinned by | CI checks | House rules |
| --- | --- | --- | --- | --- |
| Rust | the [Rust API Guidelines](https://rust-lang.github.io/api-guidelines/) | a toolchain file in the repository: Tile Lite Elite's `rust-toolchain.toml` | `rustfmt` in its default style and Clippy's default lints, a warning failing the build | the [doc-comment rules](#comments-in-code) |
| Python | [PEP 8](https://peps.python.org/pep-0008/) | nothing: CI's runner image | none | the standard library only |
| shell | the [Google Shell Style Guide](https://google.github.io/styleguide/shellguide.html) | nothing | none | Bash, under `set -euo pipefail` |

The inline-comment rules of [*Comments in code*](#comments-in-code) apply to
every language; the doc-comment rules are Rust's. Review is the only check of
Python and shell against their standards. Other files (TypeScript, JavaScript,
SQL, awk, bats, HTML, CSS, YAML) have no standard named here.

**Pinning a version in the repository** makes CI, the release build and a
developer's machine build with the same one, and makes a bump a commit.

**Python uses the standard library only**, so a script runs on a bare CI
runner and in a fresh cloud session with nothing to install.

**A shell script runs under `set -euo pipefail`**, set at its top or by a
shared library it sources first (Dark Portal's `sizing/lib.sh`). Four kinds
are excepted:

- a hook that cannot refuse (a Claude Code hook, or a git hook such as
  `post-merge`) and a session's setup script, which must never stop the
  session or command they serve: each leaves out `-e`, or the whole `set`
  line, and says why in its header;
- a check that runs every step and reports all its failures (the programme's
  `check-docs.sh`, Tile Lite Elite's `verify.sh`): it runs under
  `set -uo pipefail` and says why in its header;
- a wrapper that only sources a shim or `exec`s another script, and the shim
  it sources;
- a library sourced by scripts that set their own options, which runs under
  theirs.

A hook that refuses, such as `pre-commit`, is under the main rule.
