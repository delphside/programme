# 1.9 Testing standards

The programme's test policy and test strategy, and the standards every
application's tests are held to. The test manager
([1.7](1.7-roles-and-responsibilities.md#test-manager)) owns this document.
Each application's testing document holds its own suites, commands and
environments: Tile Lite Elite's is
[4.3.3 §2.2](https://github.com/delphside/tile-lite-elite/blob/main/docs/4.3.3-testing-ci-and-release.md#22-running-tests).
The terms are those of the
[International Software Testing Qualifications Board](https://www.istqb.org/)
(ISTQB), and each level that has an ISTQB counterpart names it.

## The test policy

Why the programme tests, and the principles every application's testing holds
to: the *test policy* of ISO/IEC/IEEE 29119-3's organizational test
documentation. The strategy below is how it is met.

- **Testing shows that a change does what its rules say, before a user finds
  that it does not.** A test that cannot fail shows nothing
  ([below](#a-new-check-is-shown-to-fail-before-it-ships)).
- **Test conditions come from the stated rules, never from the code.** Each
  application's rules documents are the source.
- **Judgement is independent of the builder.** The thread that builds a change
  writes its automated tests and runs its technical tests. The test manager, a
  different thread, approves each project's or work package's test approach
  before it leaves `Design and Test Approach`: a sign-off, which no tool
  enforces yet. Before a release is made, it checks the regression results on
  rehearsal and reports to the owner, who judges whether rehearsal passed. A
  fresh
  `test-designer` agent derives test conditions without reading the code.

## The test strategy

The *test strategy* is the set of test levels that holds across every change.
A *test approach* is the strategy applied to one project, under its *Test
approach* heading ([1.2](1.2-change-lifecycle.md#2-the-rules)).

| level | what it shows | where it runs | whose move | where it is written |
| --- | --- | --- | --- | --- |
| automated tests (component, integration and system) | each piece of logic and each script does what its rules say | CI | Claude writes them; CI runs them | in code; the application's testing document says how they run |
| functional user tests (user acceptance) | the change does what its users need | the application's user-testing environment, from the branch tip | the owner | the project's `Functional user tests` task list |
| technical tests (operational acceptance) | the change deploys, and behaves on production-like hardware | the application's rehearsal environment, from the branch tip | Claude | the project's `Technical tests` task list |
| regression (ISTQB's regression testing) | `main` as a whole still works, before a release is made | rehearsal, from `main`'s tip, by the release model in [1.2](1.2-change-lifecycle.md#making-a-release-then-deploying-it) | Claude runs it; the test manager checks the results and reports; the owner judges it passed | the application's release procedure |
| post-deployment checks | each requirement holds where its users are | production | as each check says | the project's post-deployment checks |

Each box in a task list names whose move it is, and the box overrides the
table's *whose move*.

An application's profile (`3.n.6`) says which of these environments it has;
Tile Lite Elite's are Preview and Rehearsal. Where an application has no
environment for a level, the project's test approach says how that level is
met.

## How a test is shaped

- **A test builds its own world.** It creates what it needs, such as a
  throwaway database, and leaves nothing behind, so CI runs it on a bare runner
  and no test's state reaches another.
- **A refusal is followed by a success.** Build the state, watch an action
  refused, remove the reason, and watch the same action succeed. A refusal
  alone passes against code that refuses everything.

How an application builds its tests is its testing document's (Tile Lite
Elite's
[4.3.3 §2.2.1](https://github.com/delphside/tile-lite-elite/blob/main/docs/4.3.3-testing-ci-and-release.md#221-how-the-tests-are-shaped)).

## A new check is shown to fail before it ships

Write the check, break the thing it watches, and see it go red; only then wire
it in. A check that has never fired cannot tell *nothing to do* from *not
looking*. A check's tests include the quiet case, where the check says
nothing, because a broken check passes that case by accident.

For example, Tile Lite Elite's `scripts/tests/*.bats` suites stub `gh`, and
feed each script a world whose answer is known.

## What tests the tooling

Documentation and tooling reach their users at the merge to `main`, with no
environment between. So **a gate that can fail open gets a test in
`scripts/tests/`, and CI runs it.** A tool that shows something is wrong does so
visibly; one that permits something is wrong silently, because a gate that has
stopped checking looks exactly like one everything passed.

Where CI cannot reach, the tool's own use is the test, before the merge: a
change to Tile Lite Elite's `deploy.sh` is tried by deploying to rehearsal.
Tooling is the one kind of change whose author is its only user, on the
machine where it already works, so it is tried somewhere else first. A test
that passes locally and fails in CI is found this way: one hid `gh` by
trimming `PATH` to `/usr/bin`, which on a runner is exactly where `gh` lives.

## How a test design specification is built

A change too big for "write some tests" to say what to write gets a *test
design specification* first: its techniques, test conditions and pass/fail
criteria. A test plan, of scope, schedule, resources and risks, is not written.

Claude copies the
[test design specification template](templates/test-design-specification.md),
whose ten headings are the parts, and a fresh `test-designer` agent derives
the conditions without reading the code
([1.1](1.1-programme-tooling.md#claudes-tooling)). The specification lives
with its change in the application's `3.n.7` change documents, and stays after
the change ships as the documentation of the regression tests it produced.

- **Rules first**, checked before anything derives from them: a wrong rule is
  wrong everywhere.
- **Coverage both ways**, rule to scenario and scenario to rule: each finds a
  different gap.
- **Tests named for the behaviour**, never for a scenario number.
- **Gaps recorded as gaps**, each saying what would make the missing test
  fail.

Tile Lite Elite's examples are
[deleting a user](../applications/tile-lite-elite/3.1.7-changes/41-user-deletion-test-design.md)
(functional) and
[rate limiting](../applications/tile-lite-elite/3.1.7-changes/25-rate-limiting-test-design.md)
(non-functional, judged by a script on rehearsal).

## What a unit test covers

[RIGHT-BICEP](https://www.oreilly.com/library/view/pragmatic-unit-testing/9781680500769/f_0051.html)
and its Boundary expansion,
[CORRECT](https://www.oreilly.com/library/view/pragmatic-unit-testing/9781680500769/f_0060.html),
from
*[Pragmatic Unit Testing](https://media.pragprog.com/titles/utj/StandaloneSummary.pdf)*
(Langr, Koskela, Loyer). Claude considers each for every change and covers
those that apply.

- **Right**: the results are correct, not merely returned.
- **Boundary**, CORRECT: **C**onformance to the expected format;
  **O**rdering; **R**ange (min, max, zero, negative); **R**eference to
  anything outside the code's control; **E**xistence (non-null, non-zero,
  present); **C**ardinality; **T**ime (ordering and timing).
- **Inverse**: relationships checked in reverse where one exists (encode and
  decode, save and load).
- **Cross-check**: the result checked by a second, independent route.
- **Error** conditions forced and confirmed handled, every path reached.
- **Performance** checked where the code has a characteristic worth a test.

The `unit-test-checklist` skill brings this list up when unit tests are
written or reviewed.
