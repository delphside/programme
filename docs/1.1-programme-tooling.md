# 1.1 Programme tooling

Every script and tool the programme manages itself with: the board, the
documents, the reports and Claude's own tooling, each linking to the document
that explains it. It is a generic programme asset, owned by Programme Tooling
([1.3](1.3-workstreams.md#programme-and-application)). An application's own
tooling, and what the owner runs by task, are in its (3+n).3.0 (Tile Lite
Elite's:
[4.3.0](https://github.com/delphside/tile-lite-elite/blob/main/docs/4.3.0-tools.md)).

**Paths are from this repository's root**, except these, which are in an
application's repository (Tile Lite Elite's, whose
[`.github/`](https://github.com/delphside/tile-lite-elite/tree/main/.github)
holds the first set):

- the `.github/` files other than `ci.yml` and `board-add.yml`;
- `.claude/cloud-setup.sh`, `.claude/programme-hook.sh`,
  `.claude/settings.json` and `docs/diagrams/`.

Each application holds only the ones it uses.

An application carries this repository as its `programme/` submodule, so
there the programme's paths are under `programme/`: the board scripts are
`programme/scripts/board/…`, the git hooks `programme/.githooks/…` (run
through the application's shim, described in
[*Two kinds of tooling*](#two-kinds-of-tooling)), the Claude hooks
`programme/.claude/hooks/…`. Each script finds the application
it works for from the repository it runs in (`scripts/board/profile.py`), so the
same file serves every application.

**This document says what each tool and agent does and how to run it, and how
Claude runs a review with the agents.** What each activity is for, how often it
runs, who runs it, how it is carried out and what it produces are
[1.4](1.4-programme-activities.md)'s.

## Two kinds of tooling

**Each script is an application asset or a generic programme asset**
([1.3](1.3-workstreams.md#programme-and-application)), decided by what it acts
on:

| | The application's tooling | The programme's tooling |
| --- | --- | --- |
| acts on | the application and the environments it runs in: building, testing, deploying, running, operating and measuring it | the programme's records and documents: issues, the board, the documents, the reports |
| a failure | costly, and can be silent: a deploy gate that fails open ships something untested | shows as a wrong or missing report, and is cheap to revert |
| owned by ([1.3](1.3-workstreams.md)) | Delivery Tooling, Operations & Infrastructure, Capacity & Performance | Programme Tooling |
| a change takes | a branch, tried where it runs (preview or rehearsal) before it merges ([1.2 §1.0](1.2-change-lifecycle.md#10-the-shape-of-a-delivery)) | nothing: straight to `main`, pre-approved |
| tested by | bats in CI, and a run on preview or rehearsal from the branch | bats or unittest in CI |

**The two kinds take two routes** ([1.2 §2.15](1.2-change-lifecycle.md#route)):
the application's tooling takes the Application Tooling route, which takes a
branch for the reason
[1.2 §2.2](1.2-change-lifecycle.md#22-when-to-branch-and-what-pre-approved-means)
gives, and the programme's takes Docs and Programme Tooling. Neither reaches
the image.

**Where a script reads both**, it goes by what it acts on: Tile Lite Elite's
`verify.sh` reads the board but judges whether the environments are right, so
it is the application's; its `check-api-errors.py` reads the code but guards the
application's own document (its API schema), so it is the application's too, and
`check-docs.sh` runs it as a step the application's technical profile names.

**The repositories say which**: the programme's scripts are in this repository,
in `scripts/board/`, `scripts/deliver/`, `scripts/docs/` and
`scripts/reports/`, with the git hooks (`.githooks/`), the Claude hooks
(`.claude/hooks/`) and their tests. The application's are in its own
repository, in four folders under `scripts/` that
follow the workstreams that own them: `develop/`, `deliver/`, `operate/` and
`measure/`, named by its technical profile's `scripts.groups`. The pre-commit
hook warns, and does not refuse, when a commit to `main` touches one of them: a
warning because some changes there, a comment or a typo, need no branch.

**An application carries a shim.** Its `core.hooksPath` is its own `.githooks`,
three files (`pre-commit`, `commit-msg`, `post-merge`) that run the hook of the
same name from `programme/.githooks`. A path into the submodule does not exist
until the submodule is initialised, and git then runs no hook and says nothing;
the shim exists in every checkout, so it refuses (`post-merge`: warns) and says
`git submodule update --init`. It also sets the submodule's own `core.hooksPath`
on each run and warns when `programme/` is not at the commit the application
records. Every rule stays in the programme's hooks. Its Claude hooks go through a
wrapper in the same way (`.claude/programme-hook.sh`): with the submodule absent
it says so in one line and exits 0.

**The submodule is read-only.** An application's `programme/` is a pin; a hook
(`.githooks/in-submodule/`, set as the submodule's own `core.hooksPath` by the
application's shim and setup) refuses a commit made inside it. Claude writes
every programme change in the live checkout, and moves the application's pin to
take it.

**Whoever runs a programme tool from an application checks its pin first**,
and moves it where the programme changed since, outside `records/` and
`applications/`:

```sh
git -C programme fetch origin main
git -C programme log --oneline "$(git rev-parse HEAD:programme)..origin/main" -- . ':!records' ':!applications'
```

To move it, from the application's root on `main` (a project branch takes it by
rebase):

```sh
git -C programme checkout origin/main
git add programme
git commit -m "<the application's stamp> the programme pin moves to <what it brings>"
git push origin main
```

A web session cannot push to `main`, so it carries the same commit in a pull
request, on a branch of its own: `pre-commit` lets the pin through on a branch
only when it is the whole commit, and does not tell a release or emergency
branch from any other, so keeping their pin is the committer's check. **A
release branch under test, and an emergency cut from a release tag, keep their
pin**: they run with the tools they were tested with.

### When GitHub refuses a read

The model reads GitHub through `sources.py`, by GraphQL, the search API and
REST. Three GraphQL or search reads have a REST route, taken when `gh` exits
non-zero, as it does with a cloud session's token:

| Read | Over REST |
| --- | --- |
| `fetch`: the snapshot of issues and pull requests | The same snapshot |
| `open_pull_requests`: another repository's open pull requests | The same list |
| `merged_pull_requests`: merged pull requests, by the search API | The same list, read from the application's and the programme's closed pull requests |

A read that also fails over REST raises `Unavailable`, the model's error for a
source that did not answer. When `gh` exits non-zero on any other GraphQL or
search read:

- `step_ages` returns the ages it has read: how long each issue has been at its
  step;
- `issues_by_number` and `issues_in_full` return what came back, and raise
  `Unavailable` only when nothing did;
- every other read raises `Unavailable`.

On either route the snapshot holds only the issue fields, not the board's
project fields.

Each agent's model is set in its file. Reviewers and the test designer run on
Opus at medium effort, since their work rests on judgement and higher effort
found no more faults. The change maker runs on Sonnet, because an Opus reviewer
follows it; Claude launches it on Opus where the work needs judgement:
documentation, code that needs new tests or tooling, and design where Sonnet's
draft is not enough. Fable is kept for work where Opus falls short, and for the
weekly review of the reviews
([1.4](1.4-programme-activities.md#what-the-digest-reviews-each-week)). The
trials behind this are R13 and R14 on delphside/tile-lite-elite#441.

**A review runs in rounds, one sequence per change**: its pull request, or its
commit straight to `main`. A *sequence* is the rounds from round 1 to the round
that stops it (step 6). Claude starts it when the change's content is complete,
before it reaches `main`.

| Part | Rule |
| --- | --- |
| who reviews | the change reviewer for a change maker's change and for a pull request carrying code; both document reviewers for a document change; all three where a change carries code and documents, or a change maker changed a document |
| a release, or anything hard to undo | one more independent reviewer, with a different brief |
| what owes rounds | code, a numbered document other than its register rows, a runbook, `CLAUDE.md`, a skill or an agent file |
| what owes none | a record ([1.3](1.3-workstreams.md#programme-and-application)), a change document other than a runbook, a report, a log or a register row: its pull request's *Review rounds* reads `None owed`; and a pull request a bot opened |
| content added after the stop | continues the same sequence, with the next round number |

A sequence runs:

1. Before round 1, Claude runs `check-docs.sh` and reads the text around the
   change, and any related text elsewhere, for claims the change makes false.
2. Claude launches each reviewer with a handover
   ([template](templates/agent-handover.md)); each reviews, then proves every
   finding and looks again.
3. Claude fixes each finding. A pre-existing one is fixed to the smallest true
   statement; anything more goes to a note in the week's digest draft or a
   requirement.
4. Claude agrees the fixes with every reviewer of the round before the next
   round's fresh reviewers start:
   1. Claude resumes them all on the fixes: the fixes' diff, the text around
      each, such as its lead sentence or a count, and any related text
      elsewhere a fix could make false, such as the same rule in another
      document.
   2. Each reviewer that made a finding confirms it is answered, and every
      reviewer reports what the fixes broke.
   3. Claude fixes what they report. A fix is *broken* while its finding is
      unanswered or it breaks something. Then:
      - every finding answered and nothing broken: Claude goes on to step 5;
      - a fix, other than a rewrite, broken at its second resumed check:
        Claude rewrites the passage it sits in whole, as a new fix, and
        returns to sub-step 1;
      - a rewrite broken at its own second check: it goes to the owner, and
        step 5 waits for the answer;
      - anything else: Claude returns to sub-step 1.
5. Claude re-reads each touched sentence against the code or file it
   describes, with its lead sentence, any count around it and the related
   text elsewhere, runs `check-docs.sh`, and records the round's lines in the
   change's review record.
6. If the round, its resumed checks included, made no material finding, the
   sequence stops.
7. Otherwise the next round starts at step 2, with fresh reviewers over the
   whole change. The handover's *Already checked* names the points earlier
   rounds settled, which the fresh reviewers do not raise again unless Claude
   has marked them *recheck*, as it does where a fix has touched one since.

A reviewer's completeness estimate is never the stop: in trial R13 every
reviewer put itself at 70 to 85%, whether it had found 40% or all.

Claude keeps each change's *review record*:

- for a pull request, in a `## Review rounds` section at the end of its
  body;
- for a change committed straight to `main` that owes rounds, in a note in
  the week's digest draft: a top-level bullet naming the commit, with its
  `doc:`, round, cost and owner lines indented under it.

The record has:

- one line per material finding, or one with `(count N)` for N findings
  listed once, such as one fault found in N places;
- each round's cost lines:
  - where the record has headings, one under each document's heading (a code
    file's heading takes none) and one before the first heading for a change
    reviewer;
  - where it has none, one for the record, the change reviewer's included;
- `- R<n> none` for a round that found none;
- one `doc:` line per document or code file reviewed;
- an `owner` line after the owner's review.

The `doc:` line's fields and each line's markers are in the tables after the
examples. For example, one document's rounds:

```text
- doc: docs/1.5-writing-documents.md; type rule; words 3026; change applied; lines 38; places 6; last review 2026-10-26; terms added 0
- R1 reader — 1.5 *Roles by name* — "you" in a table cell (also truth)
- R1 truth — 1.5 *What is true now, with at most a line of reason* — a count left wrong
- R1 reader — 1.5 *What is true now, with at most a line of reason* — a count the fix made wrong (from a fix to R1 truth) (on resume)
- R1 cost: reader 60k, 80%, 2 runs; truth 90k, 75%, 2 runs
- R2 reader — 1.5 *Brevity is the use case* — a clause stated twice (from a fix to R1 truth)
- R2 truth — 1.5 *One fact, one home* — a rule restated in a second document (missed in R1)
- R2 cost: reader 50k, 85%, 2 runs; truth 70k, 80%, 2 runs
- R3 none
- R3 cost: reader 40k, 90%; truth 60k, 85%
- owner — reviewed, none
```

Where each line goes:

- a record of one document or code file needs no heading;
- a record of more than one gives each a `####` heading naming its path,
  inside the `##` section, with its lines under it; `####` headings there
  are for nothing else;
- a round's lines over the whole change, such as a change reviewer's cost
  and `R<n> none` lines, go before the first heading and are the record's;
- a change reviewer's finding goes under the file it concerns, or before the
  first heading when it spans several;
- the owner's line is the record's too: it goes last and may name a document
  in its text;
- a change committed straight to `main` has no headings.

A large review, with headings, the record's own lines and a finding listed
once with a count:

```text
- R1 cost: change 80k, 85%, 2 runs
- R2 cost: change 50k, 90%

#### docs/1.2-change-lifecycle.md
- doc: docs/1.2-change-lifecycle.md; type rule; words 16878; change correction; lines 212; places 31; last review 2026-10-26; terms added 0
- R1 reader — 1.5 *Wrap prose at 80 characters* — opening paragraphs run past 350 characters
- R1 truth — 1.5 *What is true now, with at most a line of reason* — a table row that no longer matches its section (count 3)
- R1 cost: reader 110k, 80%, 2 runs; truth 140k, 75%, 2 runs
- R2 none
- R2 cost: reader 60k, 90%; truth 70k, 85%

#### .claude/agents/change-maker.md
- doc: .claude/agents/change-maker.md; type agent; words 846; change new-procedure; lines 25; places 2; last review never; terms added 1
- R1 none
- R1 cost: reader 90k, 85%, 2 runs; truth 100k, 85%, 2 runs
- R2 none
- R2 cost: reader 40k, 90%; truth 50k, 90%

- owner — reviewed, none
```

Each code file a change touches, by pull request or committed straight to
`main`, has its own `doc:` line, with `type code` and `change code`, whether or
not the change also carries documents. For a code file, `last review` is
`never` unless it has had a whole review.

The `doc:` line carries the document's inputs, which are known before the
review; the other lines are what the review found. Its form is `- doc: <path>`
then fields in any order, each `<key> <value>`, all separated by `;`:

| Field | Value |
| --- | --- |
| `type` | the document's largest part: `rule` (rules or process, such as a 1.x document or `CLAUDE.md`), `procedure` (a how-to guide that is not a skill, an agent or a runbook, such as Tile Lite Elite's 4.3.3), `reference` (checked against code or a system, such as an application's (3+n).4), `design` (how something is built, and why), `record` (a log, register or report), `template`, `agent`, `skill`, `readme`, `runbook` (the steps of one activity or delivery, run by hand) or `code` (source or a script) |
| `change` | the change's largest part: `correction` (text made true, no new rule), `applied` (changes already agreed, applied), `new-rule`, `new-term` (a defined term, no new rule), `new-procedure` or `code` (a code file's own line, or a document whose change is mostly the code it describes) |
| `words` | the document's words after the change, as `wc -w` counts the file as committed: a whole number from 1, no comma or `k` |
| `lines` | lines added plus lines removed in it, in the change's diff (the pull request's range, or the commit's): a whole number, which may be 0 |
| `places` | the separate places changed in it: the hunks, counted by their `@@` lines, in the same diff run with `git diff -U0`; a whole number, which may be 0 |
| `last review` | the date, as `YYYY-MM-DD`, of its previous whole review, or `never`; a *whole review* is one of the whole document by both document reviewers, as a `document-review` makes |
| `terms added` | the defined terms the change introduces: a whole number |

A field in any other form, or a second one for a key, is not read. What the
digest does with such a field is
[1.4](1.4-programme-activities.md#what-the-digest-reviews-each-week)'s.

| Line or marker | Meaning |
| --- | --- |
| `R<n> <reviewer> — <rule> — <finding>` | a material finding: round, reviewer as one word (`reader`, `truth` or `change`), the rule it cites |
| `(count N)` | N findings listed once: the line is N material findings, each credited as the line's reviewers are; exactly `(count N)`, N a whole number from 1, once on a finding line, the owner's included, among its other markers |
| `(also <reviewer>)` | both reviewers made it; one line |
| `(from a fix to R<n> <reviewer>…)` | caused by the fix to an earlier finding, naming its round and every reviewer who made it |
| `(from a fix to owner)` | caused by the fix to the owner's finding |
| `(from a fix)` | older records: names no finding |
| `(on resume)` | made in a resumed check of its own round; after the finding's `(from a fix to …)` marker where it has one |
| `(missed in R<n>)` | an earlier round could have found it |
| `R<n> cost: <reviewer> <tokens>k, <estimate>%, <runs> runs; …` | each reviewer's tokens as its runs report them, resumed checks included, its completeness estimate in that round, and its runs: its first run and each resumed check; `, <runs> runs` is left out for one run |
| `R<n> none` | the round made no material finding |
| `doc: <path>; …` | a reviewed document's inputs, in the form the fields table gives |
| `None owed` | the section's opening words, for a change the *what owes none* row names, other than a bot's pull request; a reason may follow |
| `owner — reviewed, none`, `owner — not reviewed` | added after the owner's review: he reviewed and found nothing, or did not review; neither is a finding, nor are older records' `owner — reviewed — none` and `owner — none`; these lines carry no marker |
| `owner — <rule> — <finding>` | a finding the owner made; `(count N)` and `(after merge, YYYY-MM-DD)` may follow |

Claude adds a finding the owner makes after the merge to the merged pull
request's record, with `(after merge, YYYY-MM-DD)`. Where the merge was in an
earlier week, Claude also adds a note to the current week's digest draft: a
top-level bullet naming the pull request, with the same `owner — …` line,
marker included, indented under it.

What the digest counts from these lines, and how it reads each, is
[1.4](1.4-programme-activities.md#what-the-digest-reviews-each-week)'s.

Work goes to an agent when it is a reading job with a defined file set, or one work package's change; triage, decisions and anything touching production stay with Claude. A good agent task:

- has a context that fits easily and holds only what the task needs, with the handover naming sections rather than whole documents;
- is one kind of problem in one area, with success and completion criteria the agent can check;
- includes examples where they frame the problem (for editing, taken from the document) and none where they would steer it (bug hunting);
- produces output that can be checked, proved by running something where it can be, and otherwise reviewed by a stronger model or a second reviewer;
- is independent of the maker's reasoning: the reviewer sees the work and the criteria, not how they were reached;
- reports for checking: every check answered, findings ranked material or minor and marked verified or inferred;
- states its limits: what it may read, what it must not change, what is out of scope;
- runs where its evidence is: a review that needs live data runs where live data can be read.
