# 1.1 Programme tooling

Every script and tool the programme manages itself with: the board, the
documents, the reports, and Claude's own tooling, each linking to the document
that explains it. It is a generic programme asset, owned by Programme Tooling
([1.3](1.3-workstreams.md#programme-and-application)). The application's tooling, and what the
owner runs by task, are [Tile Lite Elite's 4.3.0](https://github.com/delphside/tile-lite-elite/blob/main/docs/4.3.0-tools.md).

**Paths are from this repository's root**, except the `.github/` files other
than `ci.yml`: those are in each application's repository, and Tile Lite
Elite's are in [its `.github/`](https://github.com/delphside/tile-lite-elite/tree/main/.github).
An application carries this repository as its `programme/` submodule, so
there they are under `programme/`: the board scripts are
`programme/scripts/board/…`, the git hooks `programme/.githooks/…` (run
through the application's shim, see below), the Claude hooks
`programme/.claude/hooks/…`. Each script finds the application
it works for from the repository it runs in (`scripts/board/profile.py`), so the
same file serves every application.

**This document says what each tool and agent does and how to run it, and how
Claude runs a review with the agents.** What each activity is for, how often it
runs, who runs it, how it is carried out and what it produces are
[1.4](1.4-programme-activities.md)'s.

## Two kinds of tooling

**Each script is an application asset or a generic programme asset**
([1.3](1.3-workstreams.md#programme-and-application)), decided by what it acts
on:

| | the application's tooling | the programme's tooling |
| --- | --- | --- |
| acts on | the application and the environments it runs in: building, testing, deploying, running, operating and measuring it | the programme's records and documents: issues, the board, the documents, the reports |
| a failure | costly, and can be silent: a deploy gate that fails open ships something untested | shows as a wrong or missing report, and is cheap to revert |
| owned by ([1.3](1.3-workstreams.md)) | Delivery Tooling, Operations & Infrastructure, Capacity & Performance | Programme Tooling |
| a change takes | a project and a branch, tried where it runs (preview or rehearsal) before it merges | nothing: straight to `main`, pre-approved |
| tested by | bats in CI, and a run on preview or rehearsal from the branch | bats or unittest in CI |

**The branch is because `main` is where every script is run from**: a
half-finished change to `deploy.sh` there breaks the next deploy or recovery.
It is the documents' rule applied to scripts, where a project's technical
documents ride its branch and the programme's change only on `main`. Each
kind is a route of its own, Application Tooling and Docs and Programme Tooling
and Docs ([1.2 §2.15](1.2-change-lifecycle.md#route)); neither reaches the
image.

**Where a script reads both**, it goes by what it acts on: `verify.sh` reads
the board but judges whether the environments are right, so it is the
application's; `check-api-errors.py` reads the code but guards the
application's own document (its API schema), so it is the application's too, and
`check-docs.sh` runs it as a step the application's technical profile names.

**The repositories say which** (delphside/tile-lite-elite#485, from #421): the
programme's scripts are in this repository, in `scripts/board/`, `scripts/docs/`
and `scripts/reports/`, with the git hooks (`.githooks/`), the Claude hooks
(`.claude/hooks/`) and their tests. The application's are in its own repository,
in four folders under `scripts/` that follow the workstreams that own them:
`develop/`, `deliver/`, `operate/` and `measure/`, named by its technical profile's
`scripts.groups`. The pre-commit hook warns, and does not refuse, when a commit to
`main` touches one of them: a warning because some changes there, a comment or a
typo, need no branch.

**An application carries a shim.** Its `core.hooksPath` is its own `.githooks`,
three files (`pre-commit`, `commit-msg`, `post-merge`) that run the hook of the
same name from `programme/.githooks`. A path into the submodule does not exist
until the submodule is initialised, and git then runs no hook and says nothing;
the shim exists in every checkout, so it refuses (`post-merge`: warns) and says
`git submodule update --init`. It also sets the submodule's own `core.hooksPath`
on each run and warns when `programme/` is not at the commit the application
records. Every rule stays in the programme's hooks. Its Claude hooks go through a
wrapper in the same way (`.claude/programme-hook.sh`): with the submodule absent
it says so in one line and exits 0.

**The submodule is read-only.** An application's `programme/` is a pin; a hook
(`.githooks/in-submodule/`, set as the submodule's own `core.hooksPath` by the
application's shim and setup) refuses a commit made inside it, and every programme change
is written in the live checkout and taken by moving the pin.

Each agent's model is set in its file. Reviewers and the test designer run on Opus at medium effort, since their work rests on judgement and higher effort found no more faults. The change maker runs on Sonnet, because an Opus reviewer follows it; Claude launches it on Opus where the work needs judgement: documentation, code that needs new tests or tooling, and design where Sonnet's draft is not enough. Fable is kept for work where Opus falls short. The trials behind this are R13 and R14 on delphside/tile-lite-elite#441.

A review runs in rounds. Each round is one reviewer: the change reviewer for a change maker's change and for any pull request carrying code, whoever wrote it; the two document reviewers for a document change (all three where a change carries code and documents, or a change maker changed a document); each is then asked to prove every finding and look again. A release, or anything hard to undo, adds one more independent reviewer with a brief different from those, and the overlap of their findings says how much is likely left. Claude runs `check-docs.sh` before each round. Before the first, Claude also reads the text around the change for claims the change makes false; before each later one, after fixing the findings, it re-reads each sentence a fix touched, with the lead sentence and any count around it, against the code or file it describes. The change is reviewed again, until a round finds no material issue; each later round's handover lists, under *Already checked*, what earlier rounds found sound for each lens ([template](templates/agent-handover.md)), so the round covers the rest. A reviewer's own estimate of its completeness is never the stopping rule: in trial R13 every reviewer put itself at 70 to 85%, whether it had found 40% or all. Claude records each document change's review in a *Review rounds* section: at the end of its pull request body, or, for a change committed straight to `main`, in a note in the week's digest draft that names the commit. It has one line per material finding, and a closing line, `- R<n> none`, for each round that found none:

```text
- R1 reader — 1.5 *Roles by name* — "you" in a table cell (also truth)
- R1 truth — 1.5 *What is true now, with at most a line of reason* — a count left wrong
- R2 reader — 1.5 *Brevity is the use case* — a clause stated twice (from a fix to R1 truth)
- R2 truth — 1.5 *One fact, one home* — a rule restated in a second document (missed in R1)
- R3 none
- owner — none
```

Each finding line gives the round (`R<n>`), the reviewer as one word (`reader`, `truth` or `change`), the rule the finding cites and the finding. A finding both reviewers made is one line, marked `(also <reviewer>)`. `(from a fix to R<n> <reviewer>)` marks one caused by the fix to an earlier finding, naming its round and every reviewer who made it, as in `(from a fix to R1 reader truth)` for a shared one; `(from a fix to owner)` marks one caused by the fix to the owner's. A bare `(from a fix)`, in older records, names no finding. `(missed in R<n>)` marks one an earlier round could have found. After the owner's review, Claude adds a line for each fault the owner found, `- owner — <rule> — <finding>`, or one `- owner — none`, or `- owner — not reviewed` where the owner does not review. What the digest counts from these lines is [1.4](1.4-programme-activities.md#what-the-digest-reviews-each-week)'s.

Work goes to an agent when it is a reading job with a defined file set, or one work package's change; triage, decisions and anything touching production stay with Claude. A good agent task:

- has a context that fits easily and holds only what the task needs, with the handover naming sections rather than whole documents;
- is one kind of problem in one area, with success and completion criteria the agent can check;
- includes examples where they frame the problem (for editing, taken from the document) and none where they would steer it (bug hunting);
- produces output that can be checked, proved by running something where it can be, and otherwise reviewed by a stronger model or a second reviewer;
- is independent of the maker's reasoning: the reviewer sees the work and the criteria, not how they were reached;
- reports for checking: every check answered, findings ranked material or minor and marked verified or inferred;
- states its limits: what it may read, what it must not change, what is out of scope;
- runs where its evidence is: a review that needs live data runs where live data can be read.
