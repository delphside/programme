# 1.4 Programme activities

**The activities that keep the programme running, and never finish**:
sweeping the board, triaging, producing the capacity plan. This document is
their home. ITIL 4 (the IT Infrastructure Library) calls this kind of ongoing
responsibility a *practice*.

**This document says what each activity is for, how often it runs, who runs
it, how it is carried out and what it produces, and owns the continual
improvement loop**: what the digest reports, the quality measures and the two
registers. What each tool and agent an activity uses does, and how to run it,
are [1.1](1.1-programme-tooling.md)'s.

## The register

**One row per activity.** `frequency` is how often it is owed, in days.
`last actioned` is derived from
[`2.3-activity-log.csv`](../records/2.3-activity-log.csv), the most recent
date logged against the activity's `id`, and is not a column here: the log
records what happened, this table what is owed.
`scripts/board/board-practices.py` reads both and joins them.

**The log is never trimmed.** `board-practices.py` uses only the latest date per
activity, so growth costs it nothing, and the full history shows whether a
cadence is being met over time. An application's delivery log (`3.n.1`) is the
same shape for the same reason.

| ID | Activity | Frequency (days) | Owner | Produces | ITIL practice |
| --- | --- | --- | --- | --- | --- |
| `capacity-plan` | Produce and review the capacity plan | 30 | Claude produces, owner reviews | a report in the application's `3.n.3-capacity-plan/` | Capacity and performance management |
| `benchmark-run` | Tile Lite Elite's: run the engine timing benchmark on rehearsal and production | 30 | Claude; the owner runs it on production | a row in `crates/server-game/examples/engine_timing_results.csv` per host | Capacity and performance management |
| `board-sweep` | Sweep the board, triage what needs it, read each permanent thread's context use ([1.7](1.7-roles-and-responsibilities.md#handing-a-role-over)), and end with project planning: order the `Candidate Project` slots ([1.2](1.2-change-lifecycle.md#the-numbered-slots-are-positions-not-names)) | 7 | Claude leads, owner joins | none — the board itself changes | Portfolio management; project management |
| `weekly-digest` | Produce the weekly digest and review it: lessons, problems, initiatives and the measures themselves | 7 | Claude | a report in `records/2.4-weekly-digest/`, by `scripts/board/board-digest.py --write` | Continual improvement |
| `improvement-review` | Review the month's digests, the registers and the initiatives | 30 | owner, with Claude | the owner's box ticked on each of the month's reports | Continual improvement |
| `reference-review` | Re-verify the stamped reference documents against the code ([1.5](1.5-writing-documents.md#the-reference-freshness-stamp)) | 7 | Claude | corrected documents, each re-stamped | Knowledge management |
| `document-review` | Re-verify the documents no other activity covers, a quarter of them each week | 7 | Claude | corrected documents | Knowledge management |

**`weekly-digest` is programme BAU (business as usual)**, with no issue. It
produces a report file, under `CLAUDE.md`'s rule for reports the programme
produces on a cadence. The weekly scheduled task starts it when due
([What starts the work](#what-starts-the-work)).

**`reference-review` re-verifies the stamped reference documents**
([1.5](1.5-writing-documents.md#the-reference-freshness-stamp)):

1. A document keeps its stamp when none of the `files` in its
   `documents.reference` entry in the application's technical profile has
   changed since the stamp: `git log <stamp>..HEAD -- <those files>`.
2. Every other document goes to the `reference-reviewer` agent, one run per
   document with only that document and the code behind it in context. The
   agent reports and changes nothing.
3. Claude reads each finding against the code, corrects the document and
   re-stamps it.
4. At the first `reference-review` after a week it did not run, Claude also
   runs `document-reviewer-truth` over each whole document sent to the agent,
   because the `reference-reviewer` agent concentrates on what changed since
   the stamp.

**`document-review` re-verifies the documents no other activity covers**, so a
fault in text no change has touched is still found.

| Part | What it is |
| --- | --- |
| in the list | every markdown file tracked by the programme's repository and each application's in [2.1](../records/2.1-applications.md), each counted once, in the repository that holds it |
| left out | stamped reference documents (`reference-review`'s); generated documents and parts; logs and reports, which record a moment; test fixtures; everything in a change folder except its READMEs and an activity's runbook |
| each week's share | a quarter of the list, rounded up: unreviewed first, then the oldest `document-review`; ties by repository, the programme's first and then 2.1's order, then by path |
| one review | both document reviewers on each document, one whole document per run, in rounds as [1.1](1.1-programme-tooling.md#claudes-tooling) says; asked also what could be cut and what should be a list, a table or a diagram ([1.5](1.5-writing-documents.md#prose-for-reasons-structure-for-facts)) |
| the record | corrections reach `main` as any document change does ([1.2](1.2-change-lifecycle.md#23-living-documents-and-the-standing-issue-that-carries-them)), with their rounds; the log row names the documents reviewed |

**`benchmark-run` is run by hand** until its job is built on Tile Lite Elite's
scheduler (delphside/tile-lite-elite#291), when this row's `owner` changes.

## Continual improvement

**The weekly digest is the measuring half of a loop, and Claude runs the
loop**, proactively, since its point is to save the owner's time. The
`weekly-digest` activity in [the register](#the-register) is its cadence, and
this section is its definition.

The loop takes four of the questions in ITIL 4's continual improvement model:

1. Where are we now? The measures.
2. Where do we want to be?
3. How do we get there? An initiative.
4. Did we get there? Next week's measures.

When a measure moves the wrong way, Claude raises an initiative without being
asked. The owner reviews the digest. An initiative's ID is `CI-` and a number,
for continual improvement.

### The quality measures

| Area | Measure | Source | In the digest |
| --- | --- | --- | --- |
| bugs | raised, closed and open | the board | yes |
| bugs | why each happened, and the stage that caught it: review, continuous integration, preview, rehearsal or production | a root-cause section filled in when a bug closes (ITIL problem management) | to build |
| code, application and tooling | a rule decided in more than one place | a duplication scanner over Rust, Python and bash | to build |
| code, application and tooling | complexity per function, and new lint warnings | clippy's cognitive complexity, radon, shellcheck | to build |
| code, application and tooling | how much of the code the tests exercise | cargo llvm-cov, coverage.py | to build |
| process | not following it: board-check findings, continuous integration red on `main`, hooks bypassed, emergency deploys | board-check.py, continuous integration and commit history | to build |
| documentation | information in the wrong place, or the same text in two documents | the placement check, the duplication scanner over markdown and the `document-reviewer-truth` agent's review of the week's changed sections against [1.5](1.5-writing-documents.md) | to build |
| documentation | unnecessary detail: describing what is not done, justification the reader does not need | the `document-reviewer-reader` agent's review of the week's changed sections against [1.5](1.5-writing-documents.md), counting what was found and removed | to build |
| the owner's time | his input on `tooling` and `documentation` issues and pull requests: comments, answers, ticked boxes | the board and GitHub's comment history | to build |

**A measure is a baseline and a trend first**, and becomes a threshold only
once a normal week is known. A measure that costs the owner more time than it
saves is dropped.

### What the digest reports

The digest reports:

- the two measures of the brake
  ([1.7](1.7-roles-and-responsibilities.md#who-decides)), programme overhead
  and what is waiting on the owner, counted and read as 1.7 sets out;
- the tooling share, which 1.7 treats as an observation;
- what landed and what was deleted;
- each part that
  [*What the digest reviews each week*](#what-the-digest-reviews-each-week)
  lists;
- what Claude decided that the owner might have decided differently: a
  judgement, and when Claude supplies none, the report says it was
  **not written**.

### What the digest reviews each week

It collates lessons learnt, and raises and tracks recurring problems and
improvement initiatives, each BAU or a project.

| Part | Where it comes from |
| --- | --- |
| lessons learnt | collated from the *Lessons learnt* section of each issue closed in the week, naming each project closed with neither lessons nor a delegation |
| lessons noted during the week | the *Notes* of the week's draft ([*Reviewing it*](#reviewing-it)) |
| document reviews | the *Review rounds* of each change merged in the week, and those in the draft's notes for changes committed straight to `main` ([1.1](1.1-programme-tooling.md#claudes-tooling)), with the digest's counts |
| review of the reviews | the report of an agent on the Fable model ([1.1](1.1-programme-tooling.md#claudes-tooling)) from the week's *Review rounds*, the counts and last week's digest: what changed, what each reviewer and round number found for its tokens and what the owner still found after them, and the lessons ranked; Claude runs the agent and writes the report under *Review of the reviews* |
| recurring problems | [the problem register](#the-problem-register): new ones marked, open ones tracked |
| improvement initiatives | [the continual improvement register](#the-continual-improvement-register): new ones marked, open ones tracked |

From the *Review rounds*, the digest gives:

- each reviewer's material findings, a shared finding counting for both;
- the findings both the reader and truth reviewers made;
- those from a fix, and of them the *crossed*, as the R2 reader line in
  [1.1's example](1.1-programme-tooling.md#claudes-tooling) is:
  - its marker names a reviewer and not the owner;
  - none of the fault's own reviewers is among those named;
- those found in a resumed check of their own round;
- those missed by an earlier round, counted and as a share of the
  reviewers' findings;
- those the owner found, one he made after a merge in an earlier week counted
  from the draft's note that names the pull request
  ([1.1](1.1-programme-tooling.md#claudes-tooling));
- the tokens per material finding in the rounds that carry cost lines:
  - in all, each finding once;
  - by reviewer, a shared finding counting for each;
  - by round number;
  - a reviewer or round with no material finding shows its tokens against 0
    findings;
- the tokens spent;
- the cost figures not read or for no reviewer, counted:
  - a cost line with no figure in k, or a figure the digest cannot read (such
    as `1,200k`), which adds nothing to the tokens;
  - a figure naming no reviewer, which counts in the tokens but for no
    reviewer;
- the findings a token rate leaves out, counted:
  - those in a round whose cost line is missing or gives no figure the digest
    reads, which every token rate leaves out;
  - in any other round, those with a reviewer for whom its cost line gives no
    figure the digest reads, each finding once, which the by-reviewer rate
    leaves out for that reviewer;
- each merged pull request with no *Review rounds* section or an empty one,
  except one a bot opened, as `<account>/<repository>#<N>`;
- each merged pull request whose *Review rounds* has text but no line the
  digest reads (a finding, a cost line, `R<n> none`, an owner line or a `doc:`
  line), except one opening with `None owed` or a bot's, as
  `<account>/<repository>#<N>` marked **unparsed**; its summary says no line
  was read;
- a table of one row per `doc:` line, with the pull request (or, for a change
  committed straight to `main`, its note), the document's path, `type`,
  `change`, `words`, `lines`, `last review` and `terms added`, and what its
  review found: its rounds (the highest round number among the lines), material
  findings, those from a fix and its tokens (the sum of its cost lines);
- the `doc:` fields not read, counted;
- the count of reviewed documents with no `doc:` line: a `####` heading with
  none, or a record that has rounds but no heading and no `doc:` line. A pull
  request that carries only code and no `doc:` line is among them.

Every count above weighs a finding or owner line by its `(count N)`
([1.1](1.1-programme-tooling.md#claudes-tooling) gives the form). A
`(count …)` in any other form, or a second on a line, is text and is counted as
not read where it stands on a finding, owner, cost or `R<n> none` line.

In the table:

- a field missing or in a form 1.1 does not give shows `?` and is counted as
  not read; a key given twice keeps its first value, and the repeat, like a key
  1.1 does not name, is counted as not read; a `doc:` line with no path makes
  no row;
- tokens show `—` where the document has no cost line, `?` where its cost
  lines give no figure the digest reads, and `NNk (partial)` where some figure
  of them was not read;
- a `doc:` line before the first heading of a record that has headings belongs
  to the record, so its rounds, findings, from a fix and tokens show `?`;
- several `doc:` lines in one block (under one heading, in a record with no
  headings, or in a commit's note) each show the block's whole outputs, so
  the rows of one block are not to be added together. A cost line before the
  first heading is the record's and is not divided among documents.

The digest drops from the text it copies, anywhere outside a code fence, a
line that is exactly `---`, a line starting `🤖 Generated with`, a bare
`https://claude.ai/code/session_…` link, and a line that is
`_Generated by [Claude Code](…)_`. A section of nothing else counts as empty.
Its notes' heading reads "From the notes below" and covers both a change with
no pull request and an owner finding made after a merge.

### The problem register

ITIL problem management: a problem is the cause behind more than one incident.
A first occurrence is left to review. **Claude raises a row once something has
happened twice:**

- the occurrences are its evidence;
- it names the initiative that addresses it, or says there is none;
- for a problem with a row, Claude considers an automatic check as its
  initiative.

Its rows are in [2.7](../records/2.7-improvement-registers.md#the-problem-register).

### The continual improvement register

ITIL's name for the list of initiatives. An initiative is BAU or a project, as
the table in [*BAU is its own triage*](#bau-is-its-own-triage) decides; an
improvement waits for the owner to pick it at the `improvement-review` first
([*Reviewing it*](#reviewing-it)).

Its rows are in [2.7](../records/2.7-improvement-registers.md#the-continual-improvement-register).

### BAU is its own triage

**BAU raises projects, and updates its own documents without an issue.** An
initiative is done as BAU, with no issue, its row in the register as its record
and its commits carrying the trailers `Activity: weekly-digest` and
`Initiative: <id>`; or it is a project, which its row names. The test is
whether the change benefits from a project's controls, decided by type of
change:

| Type of change | Done as BAU | A project |
| --- | --- | --- |
| `documentation` | BAU's own documents (this one, the reports, the log); correcting misplaced, duplicated or unnecessary text in any document | none: a new or changed rule in a process document is the owner's decision, and BAU applies it once made |
| `tooling` | changing an existing script, check, test or hook | a new tool or dependency; a new or changed gate on what reaches production |
| `bug` | in the tooling | in the application: it ships in a release |
| `functional`, `cosmetic`, `non-functional` | never | always: it reaches the application's users |

**An initiative that needs regular progress is also a reason for a project**, so
it is progressed on the board as well as mentioned each week.

### Reviewing it

| Who | How often | What |
| --- | --- | --- |
| Claude | weekly, when the digest is written, and more often while an initiative is running | the week's lessons, notes and measures for new problems and initiatives, updating both registers; and whether each section and measure is still earning its place: one that led to no action in four weeks is dropped, and the digest says so |
| the owner | whenever he wants, and officially monthly, the `improvement-review` activity | the month's digests; he says when a review is done and Claude ticks his box and logs it, so the owner edits no file to review. A report then follows `CLAUDE.md`'s rule for reports: it may be regenerated until his review, and afterwards is corrected but never reworked |

**Claude sorts each change the weekly review proposes into a fix or an
improvement:**

- a *fix* cites what went wrong and what it cost the owner, and goes ahead:
  BAU or a project, by its type;
- an *improvement* makes something that works better: Claude adds it to the
  continual improvement register, and it waits for the `improvement-review`,
  where the owner picks what to take.

Review rounds are neither, and stay: the weekly review accepts the tokens they
spend as their cost, and judges them by what the owner still finds after them,
the fewer the better.

**Every lesson and note ends with a conclusion**, decided at the weekly
review. In the draft's *Notes*, after its opening placeholder line:

- where there are top-level dash bullets, each is one note, except a round,
  cost, owner or `doc:` line, which belongs to the note above it; text before
  the first takes no conclusion;
- where there are none, the whole text is one note.

The usual conclusions are these; any other is stated with what it rests on:

| Conclusion | Says |
| --- | --- |
| initiative | which `CI-` row |
| monitor | which `P-` row or measure |
| process changed | what changed, and where |
| no action | why |

The digest leaves each conclusion for Claude to decide, and Claude's weekly
review is done once every lesson and note has one.

Each report ends with a box for each review. **Notes between digests** go in the
next week's report:

1. `board-digest.py --write` writes the current report, and next week's as a
   draft holding only a *Notes* section.
2. The owner or Claude adds to the draft during the week.
3. Next week, `--write` keeps the notes and fills in the rest.

**A thread records a lesson in the draft when it learns it**, as a records
change on programme `main`
([1.2](1.2-change-lifecycle.md#a-session-that-cannot-push-to-main)).

## Reading the register

`scripts/board/board-practices.py` lists every activity and when it was last
done, with the frequency of an overdue one; `--json` gives every activity's
frequency ([1.1](1.1-programme-tooling.md#the-board)).
Overdue means `today − last actioned > frequency`. An activity never logged is
overdue from the day it enters this table — the log has nothing to say it was
ever done, and *never done* and *not yet due* must not read alike.

## The two readers

Each reads this register and the log, and reports on its own.

| Reader | Fires | For |
| --- | --- | --- |
| the session-start hook, `inbox-hook.sh` | each local session of an application that wires it | Claude, at the start of the session |
| a scheduled GitHub Actions workflow | weekly on Mondays, before the task in [*What starts the work*](#what-starts-the-work) | the owner, during an absence — the one gap the session-start report and `board-actions.py` leave |

Tile Lite Elite runs the workflow:
[`programme-activities.yml`](https://github.com/delphside/tile-lite-elite/blob/main/.github/workflows/programme-activities.yml)
([1.1](1.1-programme-tooling.md#the-board)).

## What starts the work

The two readers report, and a scheduled task starts the work:

1. The scheduled task, *Programme activities weekly*, wakes the demand
   manager's permanent thread
   ([1.7](1.7-roles-and-responsibilities.md#demand-manager)) every Monday at
   08:48 London time, after the workflow's run.
2. That thread reads the register against the log.
3. It starts a thread for each activity that is overdue or due within two
   days.

A handover re-points the task
([1.7](1.7-roles-and-responsibilities.md#handing-a-role-over)).

## Design notes

- **A log, and no date derived from an artefact's age**: `board-sweep`
  produces no artefact, and the log records the performance, which every
  activity has.
