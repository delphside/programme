# 1.4 Programme Activities

**The activities that keep the programme running, and never finish.** Every
container elsewhere in this document set is a thing that changes and then
stops: a requirement becomes a project, a project delivers, a delivery closes.
Sweeping the board, triaging, producing the capacity plan: none of these
close. This document is their home. ITIL 4 calls this kind of ongoing
responsibility a **practice** (delphside/tile-lite-elite#407).

**This document says what each activity is for, how often it runs, who runs
it, how it is carried out and what it produces, and owns the continual
improvement loop**: what the digest reports, the quality measures and the two
registers. What each tool and agent an activity uses does, and how to run it,
are [1.1](1.1-programme-tooling.md)'s.

## The register

**One row per activity.** `frequency` is how often it is owed, in days.
`last actioned` is not stored here — it is derived from
[`2.3-activity-log.csv`](../records/2.3-activity-log.csv), the most recent
date logged against the activity's `id`. Keeping it out of this table is
deliberate: a frequency and a last-done date are different kinds of fact, one
about the programme and one about what happened, and this document is the
first kind. `scripts/board/board-practices.py` reads both and joins
them.

**The log is never trimmed.** The check only reads the latest row per
activity, so growth costs it nothing — at four weekly and three monthly
activities, a year is about 250 rows regardless. What a full history
buys is the evidence a **continual improvement** review would need — whether a
cadence is actually being met, not just met on the day somebody looked — and
that is exactly what pruning would remove. An application's delivery log (`3.n.1`) is the
same shape for the same reason.

| id | activity | frequency (days) | owner | produces | ITIL practice |
| --- | --- | --- | --- | --- | --- |
| `capacity-plan` | Produce and review the capacity plan | 30 | Claude produces, owner reviews | a report in the application's `3.n.3-capacity-plan/` | Capacity and performance management |
| `benchmark-run` | Tile Lite Elite's: run the engine timing benchmark on rehearsal and production | 30 | Claude; the owner runs it on production | a row in `crates/server-game/examples/engine_timing_results.csv` per host | Capacity and performance management |
| `board-sweep` | Sweep the board, triage what needs it, read each permanent thread's context use ([1.7](1.7-roles-and-responsibilities.md#handing-a-role-over)), and end with project planning: order the `Candidate Project` slots ([1.2](1.2-change-lifecycle.md#the-numbered-slots-are-positions-not-names)) | 7 | Claude leads, owner joins | none — the board itself changes | Portfolio and project management |
| `weekly-digest` | Produce the weekly digest and review it: lessons, problems, initiatives and the measures themselves | 7 | Claude | a report in `records/2.4-weekly-digest/`, by `scripts/board/board-digest.py --write` | Continual improvement |
| `improvement-review` | Review the month's digests, the registers and the initiatives | 30 | owner, with Claude | the owner's box ticked on each of the month's reports | Continual improvement |
| `reference-review` | Re-verify the stamped reference documents against the code ([1.5](1.5-writing-documents.md#the-reference-freshness-stamp)) | 7 | Claude | corrected documents, each re-stamped | Knowledge management |
| `document-review` | Re-verify the documents no other activity covers, a quarter of them each week | 7 | Claude | corrected documents | Knowledge management |

**`weekly-digest` is programme work, not a project's.** It is a report file,
under `CLAUDE.md`'s rule for reports the
programme produces on a cadence, so the series outlives the decision that
started it. The weekly scheduled task starts it when due
([What starts the work](#what-starts-the-work)).

**`reference-review` re-verifies the stamped reference documents**
([1.5](1.5-writing-documents.md#the-reference-freshness-stamp)). A document
keeps its stamp when none of the files in its row of the `reference-reviewer`
agent's table has changed since the stamp (`git log <stamp>..HEAD -- <those
files>`). Every other document
goes to the agent, one run per document with only that document and the code
behind it in context. The agent reports and changes nothing; Claude reads each
of its findings against the code, corrects the document and re-stamps it.
At the first `reference-review` after a week it did not run, Claude also runs
`document-reviewer-truth` over each whole document sent to the agent, because
the `reference-reviewer` agent concentrates on what changed since the stamp.
The truth reviewer's rounds carry *Already checked* forward
([1.1](1.1-programme-tooling.md#claudes-tooling)), so together they cover the
whole of a long reference document.

**`document-review` re-verifies the documents no other activity covers**, so a
fault in text no change has touched is still found.

| Part | What it is |
| --- | --- |
| in the list | every markdown file tracked by the programme's repository and each application's in [2.1](../records/2.1-applications.md), each counted once, in the repository that holds it |
| left out | stamped reference documents (`reference-review`'s); generated documents and parts; logs and reports, which record a moment; test fixtures; everything in a change folder except its READMEs and an activity's runbook |
| each week's share | a quarter of the list, rounded up: unreviewed first, then the oldest `document-review`; ties by repository, the programme's first and then 2.1's order, then by path |
| one review | both document reviewers on each document, one whole document per run, in rounds as [1.1](1.1-programme-tooling.md#claudes-tooling) says; asked also what could be cut and what should be a list, a table or a diagram ([1.5](1.5-writing-documents.md#prose-for-reasons-structure-for-facts)) |
| the record | corrections reach `main` as any document change does ([1.2](1.2-change-lifecycle.md#23-living-documents-and-the-standing-issue-that-carries-them)), with their rounds; the log row names the documents reviewed |

**`benchmark-run` is run by hand until delphside/tile-lite-elite#400 ships a scheduler.** Once
Tile Lite Elite's Capacity Planning jobs move onto it, this row's `owner` changes and the
frequency may too — delphside/tile-lite-elite#291's design note records that as the open question.

## What has no row yet, and why that is recorded rather than hidden

Mapping the programme against ITIL's 34 practices (delphside/tile-lite-elite#407) found three with
nothing behind them at all:

| practice | state |
| --- | --- |

**Not given invented cadences here.** A row in the table above is a commitment
somebody has to meet; inventing one to fill a gap would be worse than leaving

to design properly, with the owner, when it is taken up.

## Continual improvement

**The weekly digest is the measuring half of a loop, and Claude runs the
loop**, proactively, since its point is to save the owner's time. It is
programme BAU, so no issue drives it: the `weekly-digest` activity above is its
cadence, and this section is its definition.

The loop is ITIL 4's continual improvement model: where are we (the measures),
where do we want to be, how do we get there (an initiative), did we get there
(next week's measures). When a measure moves the wrong way, Claude raises an
initiative without being asked. The owner reviews the digest.

### The quality measures

| area | measure | source | in the digest |
| --- | --- | --- | --- |
| bugs | raised, closed and open | the board | yes |
| bugs | why each happened, and the stage that caught it: review, CI, preview, rehearsal or production | a root-cause section filled in when a bug closes (ITIL problem management) | to build |
| code, application and tooling | a rule decided in more than one place | a duplication scanner over Rust, Python and bash | to build |
| code, application and tooling | complexity per function, and new lint warnings | clippy's cognitive complexity, radon, shellcheck | to build |
| code, application and tooling | how much of the code the tests exercise | cargo llvm-cov, coverage.py | to build |
| process | not following it: board-check findings, CI red on `main`, hooks bypassed, emergency deploys | board-check.py, CI and commit history | to build |
| documentation | information in the wrong place, or the same text in two documents | the placement check, the duplication scanner over markdown and the `document-reviewer-truth` agent's review of the week's changed sections against [1.5](1.5-writing-documents.md) | to build |
| documentation | unnecessary detail: describing what is not done, justification the reader does not need | the `document-reviewer-reader` agent's review of the week's changed sections against [1.5](1.5-writing-documents.md), counting what was found and removed | to build |
| the owner's time | his input on `tooling` and `documentation` issues and pull requests: comments, answers, ticked boxes | the board and GitHub's comment history | to build |

**A measure is a baseline and a trend first**, and becomes a threshold only
once a normal week is known. A measure that costs the owner more time than it
saves is dropped.

### What the digest reports

The digest reports the brake's two measures, programme overhead and what is
waiting on the owner, counted and read as
[1.7](1.7-roles-and-responsibilities.md#who-decides) sets out, with the tooling
share that 1.7 treats as an observation. It also reports what landed and what
was deleted; each part that
[*What the digest reviews each week*](#what-the-digest-reviews-each-week)
lists; and what Claude decided that the owner might have decided differently.
That last part is a judgement; when Claude supplies none, the report says it
was **not written**.

### What the digest reviews each week

It collates lessons learnt, and raises and tracks recurring problems and
improvement initiatives, each of which may be BAU only or a project.

| Part | Where it comes from |
| --- | --- |
| lessons learnt | collated from the *Lessons learnt* section of each issue closed in the week, naming each project closed with neither lessons nor a delegation |
| lessons noted during the week | the *Notes* of the week's draft |
| document reviews | the *Review rounds* of each change merged in the week, and those in the draft's notes for changes committed straight to `main` ([1.1](1.1-programme-tooling.md#claudes-tooling)), with the digest's counts |
| review of the reviews | a Fable agent's report from the week's *Review rounds*, the counts and last week's digest: what changed and the lessons ranked; Claude runs the agent and writes the report under *Review of the reviews* |
| recurring problems | the problem register below: new ones marked, open ones tracked |
| improvement initiatives | the continual improvement register below: new ones marked, open ones tracked |

From the *Review rounds*, the digest counts each reviewer's material findings,
crediting a shared finding to both. It also counts the findings both the reader
and truth reviewers made, those from a fix, those missed by an earlier round
and those the owner found. It counts as *crossed* each fault from a fix to a
finding that only other reviewers made, as the R2 reader line in
[1.1's example](1.1-programme-tooling.md#claudes-tooling) is: two reviewers
pulling the same text different ways. A fault from a fix to the owner's
finding, or with a bare `(from a fix)`, counts only as from a fix. It gives the
share of findings an earlier round missed, and the tokens spent per material
finding in the records that carry cost lines. It lists each merged pull
request with no *Review rounds* section or an empty one, except one a bot
opened.

**BAU is its own triage, so it raises projects, not requirements.** Owner,
2026-09-27: *"bau can update its own documents without an issue"*, and *"I
don't think bau will typically be raising requirement issues, because it is
effectively triaging requirements itself."* An initiative is done as BAU, with
no issue, its row here as its record and its commits carrying the trailers
`Activity: weekly-digest` and `Initiative: <id>`; or it is a project, which its
row names. Which, by type of change, not by budget or effort, which the programme does not measure:

| type of change | done as BAU | a project |
| --- | --- | --- |
| `documentation` | BAU's own documents (this one, the reports, the log); correcting misplaced, duplicated or unnecessary text in any document | none: a new or changed rule in a process document is the owner's decision, and BAU applies it once made |
| `tooling` | changing an existing script, check, test or hook | a new tool or dependency; a new or changed gate on what reaches production |
| `bug` | in the tooling | in the application: it ships in a release |
| `functional`, `cosmetic`, `non-functional` | never | always: it reaches players |

**An initiative that needs regular progress is also a reason for a project**, so
it is progressed on the board rather than only mentioned each week (owner,
2026-09-27).

### Reviewing it

| who | how often | what |
| --- | --- | --- |
| Claude | weekly, when the digest is written, and more often while an initiative is running | the week's lessons, notes and measures for new problems and initiatives, updating both registers; and whether each section and measure is still earning its place: one that led to no action in four weeks is dropped, and the digest says so |
| the owner | whenever he wants, and officially monthly, the `improvement-review` activity | the month's digests; he says when a review is done and Claude ticks his box and logs it, so no review means editing a file. A report is fixed once his review has covered it, except for a reference whose target moves, and may be regenerated until then |

**Every lesson and note ends with a conclusion**, decided at the weekly
review. In the draft's *Notes*, after its opening placeholder line:

- where there are top-level dash bullets, each is one note, except a round,
  cost or owner line, which belongs to the note above it; text before the
  first takes no conclusion;
- where there are none, the whole text is one note.

The usual conclusions are these; any other is stated with what it rests on:

| conclusion | says |
| --- | --- |
| initiative | which `CI-` row |
| monitor | which `P-` row or measure |
| process changed | what changed, and where |
| no action | why |

The digest leaves each one to decide, and Claude's weekly review is not done
while any is.

Each report ends with a box for each review. **Notes between digests** go in the
next week's report, which starts as a draft holding only a *Notes* section as
soon as the current one is written. The owner or Claude adds to it during the
week, and writing the report keeps the notes and fills in the rest. **A thread
records a lesson there when it learns it**, as a records change on programme
`main` ([1.2](1.2-change-lifecycle.md#a-session-that-cannot-push-to-main)).

## Reading the register

`scripts/board/board-practices.py` lists every activity, its frequency and
when it was last done ([1.1](1.1-programme-tooling.md#the-board)).
Overdue means `today − last actioned > frequency`. An activity never logged is
overdue from the day it enters this table — the log has nothing to say it was
ever done, and *never done* and *not yet due* must not read alike.

## Two readers, not one channel

Both read this register and the log; neither delivers to the other.

| reader | fires | for |
| --- | --- | --- |
| the session-start hook | every session | Claude, at the start of each session |
| a scheduled GitHub Actions workflow | Mondays, 07:00 UTC | the owner, during an absence — the one gap the session-start report and `board-actions.py` leave |

The workflow is in each application's `.github/workflows/`; Tile Lite Elite's
is [`programme-activities.yml`](https://github.com/delphside/tile-lite-elite/blob/main/.github/workflows/programme-activities.yml)
([1.1](1.1-programme-tooling.md#the-board)).

## What starts the work

The two readers report, and a scheduled task starts the work. The task,
*Programme activities weekly*, wakes the demand manager's permanent thread
([1.7](1.7-roles-and-responsibilities.md#demand-manager)) every Monday at 08:48
London time, after the workflow's run. That thread reads the register
against the log and starts a thread for each activity that is overdue or due
within two days.

A handover re-points the task
([1.7](1.7-roles-and-responsibilities.md#handing-a-role-over)).

## Why a log and not a date derived from an artefact

An earlier design derived *due* from the age of the newest file an activity
produces. The owner rejected it:

> Deriving actions from the presence or absence of a document seems fragile to
> me. I think we need to document the activities we do and how often and have
> a record of the activities we have done, or the last date each one was done.

**The decisive reason is not fragility, it is coverage.** `board-sweep`
produces no artefact at all, so an artefact-age rule could never have covered
it while looking like a general answer. The log records the *performance*,
which every activity has whether or not it leaves a file behind.
