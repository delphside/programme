# 1.3 Workstreams

The programme delivers change through workstreams. Each owns a part of what
the programme maintains and a named set of artefacts. A workstream is
unbounded, with no end date and no scope to complete; the projects under it
end. It is defined by this document and the `Workstream` issue field, and by
nothing else. The roles that work within them, and who decides what, are
[1.7](1.7-roles-and-responsibilities.md).

This document is generic: it would apply to any application the programme
takes on. Each application's workstreams are a record of its own
([below](#each-applications-workstreams)).

## Programme and application

The **application** is the thing the programme exists for: its code, its
environments, production. The **programme** is the organisation that owns,
operates, maintains and enhances it. Everything maintained is in one of three
classes, and the class decides how it changes:

| class | is | examples | changes |
| --- | --- | --- | --- |
| generic programme assets | how the programme works, whatever the application | processes, role definitions, templates, the programme's tooling | on `main` |
| programme records | instances produced by operating the programme, carrying an application's content | issues, the capacity plan, the delivery log, the workstream list, the application profile, who holds each role | on `main`, as the programme operates |
| application assets | the application itself | the code, its design and technical documents, its tooling, its environments | through a project and its branch ([1.2 §2.2](1.2-change-lifecycle.md#22-when-to-branch-and-what-pre-approved-means)) |

**The test for generic:** taken to a different application, it would still
apply. A generic process names and describes each asset it needs; each
application develops its own instance. So the line runs between an asset's
definition and its instance, not between documents, and where one document
holds both, the instance is a record of the application's own.

**Where a record describes the application's shape**, such as the profile's
list of what ships, a project that changes that shape updates the record on
`main` when the project merges.

`scripts/board/documents.py` applies the classes to documents, and
[1.1](1.1-programme-tooling.md#two-kinds-of-tooling) to scripts.

### More than one application

The programme runs more than one application, and they stay independent:

- **Each application has a repository of its own**, holding its application
  assets: the code and the technical information that travels with it.
- **The programme has a repository of its own**, holding the generic
  programme assets once and every programme record. It has a folder for each
  application it manages, saying how that application fits into the
  programme and holding the records operating it produces, its projects'
  change documents included. Every application consumes the generic assets
  rather than copying them (delphside/tile-lite-elite#485).
- **A project spans the two.** Its change document and the records it
  updates, such as the delivery log, are commits to the programme
  repository, with no branch. Its branch is in the application's repository
  and carries the code and the application's design documents.
- **No application depends on another.** Each has its own containers, edge
  proxy and deploy, and can move to a machine of its own without changing the
  others, so no release waits on another application's.
- **What the applications share is run as an application of its own**: the
  hosts' capacity, infrastructure, networking and security, in a repository
  of its own and owned by Operations & Infrastructure (delphside/tile-lite-elite#486). The others
  depend on it only as their host. A change to a shared host is its delivery,
  and each hosted application verifies itself afterwards. Where an
  infrastructure project affects a hosted application, by a change or only by
  its regression testing, it raises a requirement in that application's
  repository and coordinates the work.

## Generic workstreams

An application adopts these, merges them, or adds domain workstreams of its
own. The first two are the programme managing itself; the rest manage the
application.

| generic workstream | owns |
| --- | --- |
| Process Definition | every process: the change lifecycle; demand and triage; bug, incident and problem management; release and deployment policy; test strategy; document standards; security policy; continual improvement; the roles, and what a workstream is; templates |
| Programme Tooling | the board model and its scripts, issue types and fields, the documentation gates, the digest, the git hooks, and Claude's skills, agents and hooks |
| Application Architecture | the application's central function, its data model, message flows and interfaces |
| Client | what a user sees, and getting a client to them |
| Security & Access | accounts, identity and permission, and the application's security controls |
| Operations & Infrastructure | the live service, run, watched and recovered, and what it runs on |
| Delivery Tooling | the application's machinery from a commit to a running environment |
| Capacity & Performance | whether the service will outgrow its infrastructure, and how fast it is |
| domain workstreams | a slot each application fills with its own subsystems |

Process and tooling are separate workstreams because they are agreed, tested
and delivered differently: a document is discussed and merged; a script earns
a test. They share one owner.

## How workstreams group

An application's workstreams fall into four groups, the way a reader looks for
them:

| group | generic workstreams |
| --- | --- |
| the application | Application Architecture, domain workstreams, Client, Security & Access |
| running it | Operations & Infrastructure, Capacity & Performance |
| delivering it | Delivery Tooling |
| the programme itself | Process Definition, Programme Tooling |

The programme's own two are not any application's: their register is
[2.6](../records/2.6-workstreams.md), and each application's links to it.

## What makes something a workstream

**A workstream is a self-contained subsystem with mechanisms of its own**:
Authentication has tokens, sessions and hashing; client management has
bundles, versions and update signals. Something with no mechanisms of its own
is a project. The application's architecture workstream is the exception: it is what remains when the self-contained subsystems are carved
out, the application's architecture and its central function together.

**The list grows when a subsystem develops mechanisms of its own**, not because
the centre has grown large.

**The boundaries are tested by the artefact lists.** If two requirements touch
the same artefacts and sit in different workstreams, the workstreams are drawn
wrongly, not the requirements ([1.2 §2.20](1.2-change-lifecycle.md#220-workstreams-overlapping-requirements-should-land-together)).
An issue belongs to the workstream whose artefacts it changes.

**A shared mechanism goes where its content is defined**, not where its
plumbing runs, and is designed to by the other workstreams
([1.2 §2.23](1.2-change-lifecycle.md#the-exception-a-shared-mechanism-is-owned-once-and-designed-to)).

**The test is what a change is for, not how it shipped.** A logging change
shipped as a release is Operations & Infrastructure's, because it changes
how the running service is watched. `Type of change` says what a change owes;
`Workstream` says who owns it.

**Where a requirement needs two workstreams' artefacts**, it is one project
carrying both, not a dispute about ownership.

## How the names are written

A workstream's name is a proper noun and is capitalised: "this project belongs
to Operations & Infrastructure". Every other title is sentence case. `&` is used rather
than `and`, because the names are field values in column headers.

## Raising a requirement

A requirement can be raised by anyone. The owning workstream triages it, and
if accepted it folds into a project that workstream runs
([1.2](1.2-change-lifecycle.md)).

## Each application's workstreams

Each application lists its own workstreams, as instances of the generic ones
above or as domain workstreams, in its workstream register
([template](templates/workstream-register.md)), `3.n.4` in
[2.1](../records/2.1-applications.md). Tile Lite Elite's is
[3.1.4](../applications/tile-lite-elite/3.1.4-workstreams.md).

## The line between process, tooling and operations

| | owns | ends at |
| --- | --- | --- |
| Process Definition | the rules and the documents that state them | it says what should happen |
| Programme Tooling | the tooling the programme manages itself with | it reports or refuses; it never deploys |
| Delivery Tooling | an application's machinery that makes a change happen: deploy, build, CI, release gates, test tooling | the release |
| Operations & Infrastructure | the service once it is live | never; it is a running concern |

A deploy is the release, so deployment tooling is Delivery Tooling's, not
operations'.
