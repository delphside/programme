# 1.6 GitHub project board

The GitHub objects the programme is run on: the issue types and fields, the
project board, labels, accounts and rules, and the strings the tooling reads
from them. Like an application's artefact register (`3.n.2`, for example
[3.1.2](../applications/tile-lite-elite/3.1.2-artefacts.md)), it is the only
record of artefacts that leave no trace in git, named as
[1.2 §2.13](1.2-change-lifecycle.md#213-the-impacted-artefacts-and-why-they-are-listed-early)
names them; each artefact's route is in
[1.2 §2.15](1.2-change-lifecycle.md#route).

## What is held in GitHub

| Artefact | Route | What it is |
| --- | --- | --- |
| `github:labels` | Other | **the programme defines two**. `folded`, in each repository where requirements are raised, says a closed requirement was absorbed into a project rather than rejected. `Release Check`, in Tile Lite Elite's repository only, marks a post-deployment check that waits for the next release ([1.2 §2.7.1](1.2-change-lifecycle.md#271-a-check-that-has-to-wait-for-a-release)). Tile Lite Elite's repository carries the labels Dependabot adds in place of GitHub's defaults; the other repositories carry GitHub's defaults, and the service desk's intake workflow adds its own labels when it first sets them ([1.8](1.8-service-desk.md#what-a-ticket-is)). Everything else that would be a label is a field |
| `github:issue bodies` | Other | GitHub Flavoured Markdown, where **a single newline is a line break**; [1.5 *Wrap prose at 80 characters*](1.5-writing-documents.md#wrap-prose-at-80-characters) says how a body is laid out |
| `github:issue types` | Other | `Requirement`, `Project`, `Decision` and `Ticket`, org-level, set when an issue is raised. `Ticket` is used only in the service desk's repository ([1.8](1.8-service-desk.md)). `Workstream` and `Index` are disabled; a disabled type reads as null through the API, so a closed issue of a disabled type reports no type |
| `github:issue fields` | Other | **issues only in practice.** GraphQL refuses a `PR_` node ID for `setIssueFieldValue`, and REST sets a field on a pull request but clears one only on an issue (`DELETE …/issue-field-values/{id}`), so a field set on a pull request is stuck until the UI removes it. A pull-request lifecycle therefore lives on the board. The programme's fields are listed in [1.2 §2.15](1.2-change-lifecycle.md#215-classifying-a-change). Pinned to `Ticket`: `Ticket Kind` and `Sender email` ([1.8](1.8-service-desk.md#what-a-ticket-is)), and `Ticket State` ([1.8](1.8-service-desk.md#a-tickets-state)). GitHub's built-ins used: `Priority`, `Effort`, `Start date`, `Target date` |
| `github:issue field Turn` | Other | a single-select issue field, id `49935304`, on every issue type: `Owner` green, `Claude` blue, `Hold` yellow ([1.2 §2.24](1.2-change-lifecycle.md#224-whose-move-it-is-the-flow-and-the-daily-sweep) says what each means). Written by the daily sweep, and by a thread where the model cannot derive the holder. Never set on a pull request. Created by the owner: an organisation setting is out of a cloud session's reach |
| `github:issue field Claimed by` | Other | a text issue field: the role working the item, then a link to the thread holding the role now, or the role alone where no thread is known |
| `github:project view Owner's turn` | Other | the owner's list of what is his: the filter `turn:Owner is:open`, grouped by `Type`, with `Requirement State` and `Turn` as columns |
| `github:issue Board flow: the stalled list` | Other | one pinned issue in the programme repository, found by this exact title. The daily sweep rewrites its body: the stalled items by role, what needs a look, a `Last complete run:` line, and at the foot the ledger, a JSON object in an HTML comment opening `<!-- board-flow-ledger`. Nobody else edits the body |
| `github:repository setting Auto-close issues` | Other | **off** in every repository (Settings, General, **Auto-close issues with merged linked pull requests**), so a merge never closes an issue ([1.2 §2.5](1.2-change-lifecycle.md#25-tracking-a-change-to-production)). The owner turns it off in each new repository |
| `github:ruleset default branch checks` | Other | **the programme repository's**: requires CI's `check` job (`board model · scripts · documents`) to pass before a commit reaches `main`. The repository admin role and the owner's account bypass it, so a commit pushed straight to `main` by either is allowed. Tile Lite Elite's ruleset of the same name is in its artefact register (3.1.2) |
| `github:project` | Other | `Tile Lite Elite Programme`, org-owned and linked to the repository. Its **views** are pre-approved to change; the fields they read are not |
| `github:project auto-add filter` | Other | **`is:issue,pr`** — one qualifier with two values. `is:issue is:pr` is two qualifiers and adds neither, while previewing a count that includes both. Set in the project's settings; there is no API for it (`updateProjectV2Workflow` does not exist), so the owner reads and changes it by hand. It watches Tile Lite Elite's repository only; every repository's open items reach the board through `board-add.yml` ([1.1](1.1-programme-tooling.md)) |
| `github:project field PR State` | Other | a **Projects v2** single-select on the board, not an issue field: `Drafting · Awaiting review · Changes requested · Approved · Merged · Closed`. **Derived from GitHub's own state, never typed**, by `scripts/board/board-pr-state.py` for the repository it runs in: each application's, and the programme's own ([1.1 *The board*](1.1-programme-tooling.md#the-board)). A repository without that workflow has its pull requests reach the board through `board-add.yml` with `PR State` unset |
| `github:owner account` | Other | **`SteveStyle`**. Not `stephenmor`, which is the email prefix and is what `--reviewer` silently accepts: `gh` reports an unknown login on stderr and creates the pull request anyway, requesting nobody. `scripts/board/create-pr.sh` defaults to it, and `board-pr-state.py` reports a pull request that requests nobody |
| `github:machine account` | Other | `SteveStyle-typed-by-Claude`. Claude's identity, so the owner can approve what Claude opens. Permitted by GitHub's Terms B.3 (one machine account beside a personal one, set up by a human, with a valid email, used only for automated tasks, the human responsible); it must not be used as a second personal account. It carries two-factor authentication |
| `github:app Claude` | Other | Anthropic's Claude Code app, installed on the organisation, with write access to the code, issues, pull requests and workflows of the repositories the owner grants it: dark-portal, infrastructure, programme, service-desk and tile-lite-elite. It is how a Claude Code session on the web reaches the repositories, the owner's fallback when away from the laptop; what such a session may do is [1.2 §2.2](1.2-change-lifecycle.md#a-session-that-cannot-push-to-main)'s |

## Which level carries which field

A field is pinned to types (org settings, Planning, Issue fields, the field,
**Pin to types**); an unpinned field is absent from the sidebar and the creation
form. Pinning does not restrict: any field can be added to any issue, so the
rule is this table and `board-check.py`.

**Each type's journey is one field named `<type> State`**: `Requirement State`,
`Project State`, `Decision State` and `PR State` on the board. The names are in
`board/model.py`.

A project whose sub-issues include projects is a *parent*; a project with a
parent is a *work package*; any other project is *standalone*
(`board/model.py`).

| Field | Requirement | Project (parent) | Project (work package or standalone) |
| --- | --- | --- | --- |
| Workstream | set at triage | yes | yes |
| Type of change | set at triage | yes | yes |
| Priority | set at triage | yes, past Scope | yes, past Scope |
| Effort | set at Scope, Options and Dependencies | yes, past Scope | yes, past Scope |
| Route | known by Candidate Project | never | yes |
| Requirement State | yes; unset is read as `Triage` | — | — |
| Turn | yes | yes | yes |
| Claimed by | when worked | when worked | when worked |
| Project State | — | yes | yes |
| Milestone | none | none | yes, except Docs and Programme Tooling |
| Parent | none | none | its parent project, for a work package |

A `Decision` carries `Workstream`, `Parent`, `Decision State`, `Turn`,
`Claimed by` and `Topic`, and a `Ticket` carries `Turn`, `Claimed by` and the
fields [1.8](1.8-service-desk.md) names. The values of each field are in
[1.2 §2.15](1.2-change-lifecycle.md#215-classifying-a-change).

## What the tooling reads, and would break on

Renaming any name or structure the tooling matches is a change routed by
[1.2 §2.2](1.2-change-lifecycle.md#22-when-to-branch-and-what-pre-approved-means).

### What else is matched, and how each breaks

This table gives how a rename breaks, for the names that have a row. It also
holds what the vocabulary does not: structures, IDs and patterns, the board's
views and filters, `config/programme.toml`, search and the project form, the
former `Route` names and the `Repository Change` prefix, and the scripts
outside `scripts/board/`, Tile Lite Elite's and the service desk's. A script
from Tile Lite Elite's repository is labelled as Tile Lite Elite's. A name with
no row here is described only by its readers in the generated table. A
programme module is named only for the function or constant a row is about,
and for the modules that read that one.

| What | Read by | Breaks how |
| --- | --- | --- |
| `Type of change` = `functional` | Tile Lite Elite's [`check-release-version.sh`](https://github.com/delphside/tile-lite-elite/blob/main/scripts/deliver/check-release-version.sh) | silently: the release gate stops finding functional work, so every patch release passes; the digest shows functional work as a type 1.7 does not name |
| the `Route` option names, and `Repository Change` as a prefix | `model.py`'s `delivered_by_merge`, and its `route_of`, which also reads the names used until 2026-10-26; `obligations.py`'s `wp-milestone` | quietly: a merged tooling package is not moved to Post-deployment, and looks blocked on a release; a Docs and Programme Tooling package is reported for having no milestone. The prefix already misses the live option `DEPRECATED Repository Change` |
| the field name `Type of change` | Tile Lite Elite's `check-release-version.sh` | the gate finds no functional work; the digest and triage checks read every issue but a `Decision` as unset |
| issue type names `Requirement`, `Project`, `Decision` | the board's `type:` view filters, Tile Lite Elite's [`deploy.sh`](https://github.com/delphside/tile-lite-elite/blob/main/scripts/deliver/deploy.sh) | the tree flattens; views empty; the digest counts each `Decision` as unset and misses each `Project` closed without lessons; `branches.py` reports a branch naming an open project as not belonging to one; Tile Lite Elite's deploy closes each shipped `Project` instead of moving it to Post-deployment, posts its *Released* comment on parents and asks a shipped `Requirement` with no milestone for one |
| label `Release Check` | Tile Lite Elite's [`deploy.sh`](https://github.com/delphside/tile-lite-elite/blob/main/scripts/deliver/deploy.sh) (`announce_release_checks`) | quietly: a check waiting for a release is reported as a post-deployment review due, and the deploy announces nothing |
| the `Decision State` option names | `model.py`'s `DECISION_TURNS` | quietly: a renamed option waits on nobody |
| the `Project State` field name | Tile Lite Elite's [`deploy.sh`](https://github.com/delphside/tile-lite-elite/blob/main/scripts/deliver/deploy.sh) | a project shows as not started; a shipped project is never advanced |
| the option `Post-deployment`, and its ID | Tile Lite Elite's `deploy.sh` sets it by ID after a release; `turn.py` matches it by name, through `PROJ_POST_DEPLOYMENT` | a release stops advancing what it ships, or the review reminder never fires |
| `IssueFieldChangedEvent` in an issue's timeline | [`board/sources.py`](https://github.com/delphside/programme/blob/main/scripts/board/sources.py)'s `step_ages`, read by `board/turn.py` and `board-check.py` | the time at a phase is unknown, and the review reminder says nothing |
| milestone titles that are versions | Tile Lite Elite's `deploy.sh` and `check-release-version.sh` | a release closes nothing, or the gate cannot find its scope |
| milestones `no-release`, `patch`, `minor`, `major`, retired ([1.2 §2.15](1.2-change-lifecycle.md#215-classifying-a-change)) and still read until Tile Lite Elite's tooling drops them | Tile Lite Elite's `deploy.sh` `placeholder_shipping` | an issue shipping under a placeholder is not reported |
| the parent link | [`board/model.py`](https://github.com/delphside/programme/blob/main/scripts/board/model.py)'s `classify` | work packages read as standalone projects, and parents as nothing special |
| `Requirement State` and its values | the board's backlog view | a requirement's journey stops being visible or checked |
| issue type name `Ticket` | the service desk's `desk/desk.py`; `model.py`'s `classify` | loudly: intake raises no Ticket and every reply is ignored; the board model reads a Ticket as an untyped Requirement |
| the field names `Ticket State` and `Sender email`, and the options `New`, `In progress` and `Waiting on sender` | the service desk's `desk/desk.py` ([1.8](1.8-service-desk.md#a-tickets-state)) | quietly: the desk logs that it could not set the field and leaves it as it was, and the board model reads no state |
| the field `Turn` and its options `Owner`, `Claude`, `Hold`, and its ID `49935304` | `config/programme.toml` `[flow.field_ids]`, read by [`board/flow.py`](https://github.com/delphside/programme/blob/main/scripts/board/flow.py), and the board's `turn:Owner` view filter | loudly: a write the sweep cannot make fails the run (exit 2); a renamed option is reported, never rewritten, and the owner's view empties |
| the field name `Claimed by` | the generated table | quietly: every claim reads as no claim |
| the title `Board flow: the stalled list`, and in its body the `<!-- board-flow-ledger` block and the `Last complete run:` line | [`board/flow.py`](https://github.com/delphside/programme/blob/main/scripts/board/flow.py) (`STALLED_LIST_TITLE`) | loudly: the sweep refuses to run when no issue has the title. An edited ledger costs the ages of the open items: the run that finds it unreadable lists it under *needs a look* and judges the items afresh. A body cleared of the ledger marker and the `Last complete run:` line reads as a first run and is not reported |
| a line under *Dependencies and related work* with `review` and a date, such as `review 2026-12-01`, beside the event waited for; and the same pattern in the last comment on a Ticket at `Pending` ([1.8](1.8-service-desk.md#how-long-a-ticket-may-wait)) | [`board/flow.py`](https://github.com/delphside/programme/blob/main/scripts/board/flow.py) (`_REVIEW_DATE`) | quietly: a hold on a named event with no date has no reason the sweep can check, so it is listed as invalid and its `Turn` rewritten; a `Pending` Ticket with none stalls after 7 days |
| label `folded` | search, and the project form's instructions | a folded requirement cannot be told from a rejected one |
| a `Review` heading in a pull request body, opening `No review owed` (not *Review rounds*) | [`board/model.py`](https://github.com/delphside/programme/blob/main/scripts/board/model.py)'s `owes_no_review`, read by `board/pr_sync.py` | a pull request that owes no owner review is reported as waiting on nobody |
| a `What is being requested` and a `What is deliberately left out` heading in a pull request body | `pr-scope-stated` in [`board/obligations.py`](https://github.com/delphside/programme/blob/main/scripts/board/obligations.py), read by `board-check.py` | loudly: `board-check.py` reports a pull request awaiting review without both |
| the field slug `type-of-change` | the board's Needs triage filter | the view renders empty, which reads as nothing to triage |
