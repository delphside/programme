# 1.5 Writing documents

The house style: how the programme's and the applications' documents are
written, and what each may hold. It covers the numbered documents, the records,
the READMEs and Claude's own files: `CLAUDE.md`, the skills and the agents. Read
it before adding to one; `CLAUDE.md` carries a summary line and points here, and
the change-a-document skill is the procedure for placing a fact.

The base is the
[Google developer documentation style guide](https://developers.google.com/style).
Where this page is silent, Google's guide applies; where the two differ, this
page wins. This page holds only the house principles and the
[deviations from Google](#deviations-from-google), each under a heading a
reviewer cites. The two document reviewers apply it to every document change
([1.1](1.1-programme-tooling.md#claudes-tooling)).

## What a numbered document holds

### Each range covers one scope

Numbers are programme-wide: one number names one document anywhere in the
programme's repositories, and equivalent documents carry equivalent numbers.

| Range | Covers |
| --- | --- |
| 1.x | the programme's definition and processes: how the programme is run, its tooling and the board |
| 2.x | programme-wide records: the applications, role holders, the activity log, the weekly digests, change documents and the programme's workstreams |
| 3.n.x | application *n*'s records, under the same suffix for every application ([2.1](../records/2.1-applications.md#what-each-applications-folder-holds)) |
| (3+n).1 | application *n*'s overviews: the requirements, architecture, design and technologies, the roadmap, current work and the documentation |
| (3+n).2 | application *n*'s end-to-end design of each functional area |
| (3+n).3 | application *n* in detail: setting it up, developing, testing, releasing, operating and measuring it |
| (3+n).4 | application *n*'s reference: every current value, and nothing else |

The (3+n).x documents are in the application's own repository.

The applications and their indexes *n* are in
[2.1](../records/2.1-applications.md).

A document belongs to the range its subject falls in, whichever workstream
owns it. Within a document, the four [Diátaxis](https://diataxis.fr/) types
(tutorial, how-to, reference, explanation) describe how to write each part.

### What is true now, with at most a line of reason

History, argument and quotations go in the issue or the commit that made the
change: they are permanent there, and they rot in a document. The exception is
the evidence named in
[*Keep the evidence, not the argument*](#keep-the-evidence-not-the-argument).

The writer checks a claim about what code does against the code itself, and the
reviewers check it again. A comment or another document can be wrong, and a
claim copied from one is wrong with it.

### One fact, one home

A fact is stated in the document that owns its subject, and every other mention
links there. **The numbered documents are complete on their own, except for a
folder's conventions.** `CLAUDE.md`, the skills, the agents and the READMEs
help a reader find and follow them, and hold only what a numbered document also
holds, except that a README is the home of its own folder's conventions
([*What a README holds*](#what-a-readme-holds)). The layout in the
[root README](../README.md) says where each kind of document lives, and an
application's document map lists every heading of its
own documents (Tile Lite Elite's is
[4.1.6](https://github.com/delphside/tile-lite-elite/blob/main/docs/4.1.6-document-map.md)),
so the home can be found before writing.

Documents outside the numbered set keep their own types:

| Kind | Where it lives |
| --- | --- |
| change documents | each application's `3.n.7-changes/`, and [`records/2.5-changes/`](../records/2.5-changes/) |
| periodic reports | [`records/2.4-weekly-digest/`](../records/2.4-weekly-digest/), and each application's `3.n.3` |
| templates | [`templates/`](templates/); how a template marks what to replace is in its [README](templates/README.md#how-a-template-is-filled-in) |
| READMEs | the folder each describes ([*What a README holds*](#what-a-readme-holds)) |

**A generated document is edited only by regenerating it.** Each application's
technical profile, `app-profile.toml`, lists its generated documents under
`documents.generated`, which
[`scripts/board/documents.py`](../scripts/board/documents.py) reads. Tile Lite
Elite's include its work in progress, 4.1.5, and its document map, 4.1.6.

### What a README holds

**Whoever creates a folder that a reader reaches by browsing, and whose
contents need explaining, gives it a README.** The README holds, in this
order:

- one or two sentences on what the folder is for;
- a table or list of what the folder holds, with each document in it linked,
  and a subfolder or a series of reports linked once as one entry;
- the conventions of the folder's own contents, where the folder has any,
  such as how a template is filled in or how a change document is laid out;
- a link to the numbered document for any other rule it mentions.

Whoever adds or removes a document in the folder updates its README.

## The reference freshness stamp

Each reference document, (3+n).4.x, listed under `documents.reference` in its
application's technical profile carries a *freshness stamp* under its title: the
commit its contents were last checked against the code. Only reference documents
have one, because they make the falsifiable claims ("these are the columns",
"this is every endpoint") that go silently wrong when the code moves. When you
re-verify a document, update the stamp; an edit alone leaves it as it is.

Re-verification is the weekly `reference-review` activity
([1.4](1.4-programme-activities.md#the-register)), against every file a document
describes.

## Where an application's settings are listed

Every setting an application has is listed in its configuration reference,
(3+n).4.1, and the weekly `reference-review` checks that none is missing. How
each kind of setting is held in the code is
[1.10](1.10-development-standards.md#where-an-applications-settings-are-held).

## Who each range is for

### Every section has an audience and a use case

The audience and the use case decide what belongs in a section. The test for a
sentence is *would this reader do the wrong thing without it*. Four faults show
a missing sentence:

- the actor is unnamed: a rule with no one to carry it out;
- a term is used before it is defined;
- the rule, its example and the tool that reads it disagree;
- a case the reader will meet is not covered.

| Range | Who is reading | What they are doing | So it carries | And leaves out |
| --- | --- | --- | --- | --- |
| (3+n).1 | somebody new to the system, or deciding scope | working out what the thing is and where it is going | the current shape, and the direction | how it came to be this way |
| (3+n).2 | whoever is about to change a functional area | making a change without rediscovering the model | the model, its constraints and what the constraints cost, with [design notes](#describe-the-choice-made-rejected-ideas-go-in-design-notes) on rejected ideas a reader might propose | step-by-step instructions, which belong in (3+n).3 |
| (3+n).3 | whoever is building, releasing or operating the application now | doing the next step correctly, under time pressure | the command first, the reasoning below it | anything that delays the reader in a hurry |
| (3+n).4 | somebody who already knows what they want | looking one fact up and leaving | every value, complete and current, with a freshness stamp | reasoning of any kind |
| 1.x | whoever is at a process step, a future project reusing the process and whoever needs to know how the programme is organised | doing the step correctly, and judging whether the process is right | the rule first, the reasoning below it | the programme's history |
| 2.x, 3.n.x | whoever reviews the programme or an application, and the tooling that reads the records | looking up what happened, what a register holds or how a change was designed | each entry in its template's shape, where it has one; a change document is as its folder's README says (Tile Lite Elite's: [3.1.7-changes/README.md](../applications/tile-lite-elite/3.1.7-changes/README.md)) | anything its template leaves out |

A 1.x document states each rule so it holds for any programme run this way, and
keeps this programme's own answer to it separate: the rule is *portable*.

`CLAUDE.md`, the skills and the agent files are read by Claude at the moment of
acting, and follow the 1.x row: the rule first, and only what the step needs.

**The one that is easiest to get wrong is (3+n).3**, because the same document
serves somebody shipping in 10 minutes and somebody deciding whether the
process is right. Tile Lite Elite's `docs/4.3.3` is the worked example: a
table of the steps at the top, then each step with where it runs, its commands
and what proves it worked, then Part 2 for the mechanisms behind them.

### Brevity is the use case

Cut a sentence the reader would not miss, and a point already made.

### A document stays under 25 KB

A document or an issue body over 25 KB is restructured. A document is split by
audience or subject into documents that each cover one scope, or cut; an issue
body moves its design into a change document and links to it. A reader, Claude
included, reads a document whole, and one that is too large to hold in mind at
once is read in parts, which is how a rule in another part is missed.

`check-docs.sh` lists the documents over the limit and `board-check.py` the
open issue bodies; both report and neither fails
([1.1](1.1-programme-tooling.md#the-documents)). At the weekly
`document-review`, Claude proposes a restructure for each and makes it as any
document change is made ([1.4](1.4-programme-activities.md#the-register)).

The limit covers every document except logs, reports, test fixtures, generated
documents, and change documents other than a change folder's README and its
runbooks. A stamped reference document is covered.

## How these documents are written

### Reader first

**Write first for somebody who needs to do something quickly and wants
pointing at what they need**, and serve every other reader afterwards. That
reader has a job in progress and knows roughly what they want. So: the command
or the rule first, an index by *intent* and the reasoning below it, where
anyone who wants it finds it and anyone else skips it.

### Prose for reasons, structure for facts

**A reader acts on a list, a table or a diagram, and reads prose for the
reason.** Each kind of content takes its form:

| Content | Form |
| --- | --- |
| steps done in order | a numbered list |
| a set of items, conditions or exceptions | a bulleted list |
| items compared on the same attributes | a table |
| a rule | one bold sentence, then its conditions as a list |
| values a reader looks up | a table |
| a command to type | a code block |
| a flow, the states a thing moves through or how components connect | a Mermaid diagram, which `check-docs.sh` parses ([1.1](1.1-programme-tooling.md#the-documents)) |
| why | a short paragraph |

Text in a list, a table or a diagram is terse: a phrase where a phrase carries
it without ambiguity. The writer restructures a paragraph holding a sequence,
a flow, two or more conditions, or a set of items into its form. Prose hides a
rule's conditions in its clauses, where a reader misses one and a writer
changing one breaks another. Google's guide has the rules for writing the lists
and tables themselves (*Lists*, *Tables*).

### Bold run-in labels

**A paragraph or list item may open with a bold label where a reader scans
for it**, such as the four kinds of evidence in
[*Keep the evidence, not the argument*](#keep-the-evidence-not-the-argument),
with these conditions:

- the label is a phrase, in sentence case;
- a colon follows it, outside the bold, and the text after the colon starts in
  lower case unless it is a name: `**Source requirements**: none`;
- where the label is the opening words of the item's own sentence, no colon
  follows: `**A measurement** that was expensive to take`;
- where tooling reads the label, it keeps the form its owning rule gives: a
  checkbox's owner ([`CLAUDE.md`](../CLAUDE.md)), a dependency
  ([1.2](1.2-change-lifecycle.md#where-a-dependency-is-recorded)) and a
  recurrence
  ([1.2](1.2-change-lifecycle.md#a-recurrence-is-a-date-in-an-issue-body));
- the items of one list either all take a label or none does.

A bold sentence or main clause is a
[bold lead sentence](#bold-lead-sentence).

### Label each box in a diagram as C4 does

**A box in a diagram that takes a C4 view gives its element's name, kind and
description, in that order**, as C4's notation does
([notation](https://c4model.com/diagrams/notation)):

- the name, in italics, as the system shows it: C4 sets it in bold, which
  Tile Lite Elite's process diagrams keep for an action somebody takes;
- the kind in square brackets, as C4 names it, with its technology after a
  colon where it has one: `[Person]`, `[Software System]`, `[Container: Bash]`,
  `[Component]`;
- a short description, where the box needs one.

```text
NODE["<i>name</i><br>[Component]<br>what it does"]
```

A group (a Mermaid `subgraph`) is titled `Kind: name`, such as `Oracle VM:
rehearsal`: the house's short form of C4's `name [Deployment Node: kind]`,
since Mermaid clips a long group title. Where a diagram is rendered with
`htmlLabels` off, the italics are a Mermaid markdown string (`*name*` inside a
backtick-quoted label), since `<i>` is printed literally there. A process
diagram takes no view and keeps its own conventions (Tile Lite Elite's
[diagram conventions](https://github.com/delphside/tile-lite-elite/blob/main/docs/diagrams/README.md#conventions-of-the-process-diagrams)).

### Give a commit's app version alongside its ID

For a commit to an application, Tile Lite Elite's `25e9e09` alone dates a change
only for somebody willing to go and look it up; `25e9e09` (app 0.4.12) places it
in the release history a reader already carries. The ID stays, because it is the
thing you can `git show`.

### Reference answers "what is there" and "what do I type"

The why belongs in an overview section or a (3+n).2 design document, so a
reader looking up a command reads only the command.

### Imply the rationale

Carry the reason in an adjective where one will do: "the safe default", "one
throwaway worktree", "a single source of truth".

### Keep the evidence, not the argument

Keep a fact somebody would otherwise have to go and re-acquire, and drop the
case once made for a decision: reasoning ages, and evidence does not. Evidence
worth keeping is one of four kinds:

- **A measurement** that was expensive to take, or is not repeatable now.
- **A negative result**: what was tried and did not work, which the current
  state cannot show.
- **An outside constraint** the artefact does not reveal: what a service will
  not do, what a tool does when you get it wrong.
- **The failure a guard exists to prevent**, without which the guard looks
  like caution and gets removed.

### Issue numbers, rarely and for a reason

Cite an issue only where a reader would change something wrongly without it.
These documents describe what is there, and provenance lives in commit
messages, which are permanent and carry their own context.

Three cases qualify:

- a design note on a rejected idea may cite the issue that argued it, when a
  later change would otherwise undo the reasoning without knowing it existed;
- a change document is about a change, so it names the change's issue;
- a temporary note names the issue that will change the text, and is deleted
  when that issue lands or is resolved.

`CLAUDE.md` is written for Claude, so it takes whatever form Claude follows
best. It cites an issue under the same three cases,
because an issue is frozen at its close and goes out of date.

### Describe the choice made; rejected ideas go in design notes

The descriptive text says what is done: Tile Lite Elite's "the tests change
the dates in the database". An aside naming a dropped option goes stale when
the decision changes.

Where a rejected option carried a real constraint, keep the constraint and drop
the comparison: Tile Lite Elite's "It must be in-module: backdating needs
`state.db`" stays true when the alternative is forgotten.

In a living document, (3+n).1 to (3+n).3 or 1.x, a rejected idea is written down
only where it is not obvious and somebody might propose it. It then goes in a
closing `## Design notes` section: one short entry each, with the constraint
that ruled it out. Change documents record what was rejected and why, as their
folder's README says (Tile Lite Elite's:
[3.1.7-changes/README.md](../applications/tile-lite-elite/3.1.7-changes/README.md)),
and this rule leaves them alone.

### Say what is the case, not what is not

A positive statement replaces *never*, *not only*, *not just*, *rather than*,
*instead of*, *no longer* and the like wherever it says the same: "each
environment has one database" in place of "there is never more than one". A
rule that forbids something is still written as one.

### Say what is, not what should be

*Should*, and a *may*, *typically* or the like qualifying a fact, describe an
intention or hedge a fact; a *may* granting a permission is a rule. "Each
environment has one database" beats "the project should use one primary
database file per environment".

### Sentence case, and names as the system shows them

Headings and table headers are in sentence case, as in Google's guide: the first
word is capitalised (`| Kind | Meaning |`). A sentence in a table cell is
punctuated as a sentence. A name keeps the capitals the system shows: board
fields and single-select values (`Project State`, `Design and Test Approach`),
issue types, labels and file names. A template follows the same rule in its
own headings and headers; its placeholders keep whatever case the filled-in
text will have.

A term is in italics where it is defined, as in Google's guide, and in plain
text after that. Italics also mark a word used as a word and a cited heading,
and in a template a placeholder
([templates](templates/README.md#how-a-template-is-filled-in)). *ID* is in
capitals, except inside a name with its own
convention, such as a field, a key or a code identifier (`issue_id`).

### Wrap prose at 80 characters

**Wrap a Markdown paragraph at 80 characters**, with these conditions:

- when editing, rewrap only the paragraphs you change, so the diff shows the
  edit;
- a table, a code line, and a link with its text and target each stay on one
  line, whatever their length;
- YAML front matter keeps each key and its value on one line, whatever its
  length, because Claude Code reads it;
- an issue or pull request body takes one line per paragraph, because GitHub
  renders its newlines.

### Application specifics only as a labelled example

A programme document (1.x, 2.x and Claude's own files: `CLAUDE.md`, the agents
and the skills) states the rule for every application, and names one
application's specifics only as a labelled example ("Tile Lite Elite's 4.3.3").

## Deviations from Google

Each is where the house differs from Google's guide, with its reason.

### British spelling

British spelling, with -ise endings (*organise*, *realise*): the owner's
choice, and the documents' practice. Names from code, tools and quotations keep
their own.

### Dates

ISO 8601, `2026-10-17`: it sorts, and matches the board and the commit stamps.

### Serial comma

No comma before the last *and* or *or* of a list (*red, white and blue*),
unless an item itself contains *and* or *or* and the list would misread
without it: British usage, and the documents' practice.

### Contractions

Full forms (*do not*, *cannot*): a negation stands out in full.

### Dashes

A spaced em dash, `word — word`, for an aside: the documents' practice.

### Quotation marks

Punctuation goes inside the quotation marks only when it belongs to the
quotation: British usage.

### Bold lead sentence

A paragraph or list item may open with its point in bold, so a reader scanning
finds it. The bold is either a whole sentence, with its full stop inside the
bold, or the sentence's main clause, which runs on after the bold.

### Document numbers as link text

A document's number is its name, so `[1.4](1.4-programme-activities.md)` is
descriptive link text.

### Roles by name

A process document names who acts (the owner, Claude, a reviewer), and *you*
addresses the reader doing a step: several roles read one document.

### Avoid *we*

Avoid *we*, which Google allows for the organisation: it hides which role acts.
