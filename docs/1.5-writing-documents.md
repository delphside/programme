# 1.5 Writing documents

The house style: how the programme's and the applications' documents are
written, and what each may hold. It covers the numbered documents, the
records and Claude's own files: `CLAUDE.md`, the skills and the agents. Read it
before adding to one; `CLAUDE.md` carries a summary line and points here, and the
change-a-document skill is the procedure for placing a fact.

The base is the [Google developer documentation style
guide](https://developers.google.com/style). Where this page is silent, Google's
guide applies; where the two differ, this page wins. This page holds only the
house principles and the [deviations from Google](#deviations-from-google),
each under a heading a reviewer cites. The two document reviewers apply it to
every document change ([1.1](1.1-programme-tooling.md#claudes-tooling)).

## What a numbered document holds

### Each range covers one scope

Numbers are programme-wide: one number names one document anywhere in the
programme's repositories, and equivalent documents carry equivalent numbers.

| range | covers |
| --- | --- |
| 1.x | the programme's definition and processes: how the programme is run, its tooling and the board |
| 2.x | programme-wide records: the applications, role holders, the activity log, the weekly digests, change documents and the programme's workstreams |
| 3.n.x | application *n*'s records, under the same suffix for every application ([2.1](../records/2.1-applications.md#what-each-applications-folder-holds)) |
| (3+n).x | application *n*'s own documents, in its own repository, in four groups: (3+n).1 overviews (the requirements, architecture, design and technologies, the roadmap, current work and the documentation), (3+n).2 the end-to-end design of each functional area, (3+n).3 the application in detail (setting it up, developing, testing, releasing, operating and measuring it), and (3+n).4 reference: every current value, and nothing else |

The applications and their indexes *n* are in [2.1](../records/2.1-applications.md).

A document belongs to the range its subject falls in, whichever workstream
owns it. Within a document, the four [Diátaxis](https://diataxis.fr/) types
(tutorial, how-to, reference, explanation) describe how to write each part.

### What is true now, with at most a line of reason

History, argument and quotations go in the issue or the commit that made the
change: they are permanent there, and they rot in a document. The exception is
the evidence named in [*Keep the evidence, not the
argument*](#keep-the-evidence-not-the-argument).

### One fact, one home

A fact is stated in the document that owns its subject, and every other mention
links there. The layout in the [root README](../README.md) says where each kind of document lives, and an application's document map lists every heading of its own documents (Tile Lite Elite's is [4.1.6](https://github.com/delphside/tile-lite-elite/blob/main/docs/4.1.6-document-map.md)), so the home can be found before writing; the
`change-a-document` skill is the procedure.

Documents outside the numbered set keep their own types: change documents in
each application's `3.n.7-changes/` and in
[`records/2.5-changes/`](../records/2.5-changes/), periodic reports in
[`records/2.4-weekly-digest/`](../records/2.4-weekly-digest/) and each
application's `3.n.3`, templates in [`templates/`](templates/). Two numbered documents are generated, and edited only by regenerating them:
[Tile Lite Elite's 4.1.5](https://github.com/delphside/tile-lite-elite/blob/main/docs/4.1.5-work-in-progress.md) and [Tile Lite Elite's 4.1.6](https://github.com/delphside/tile-lite-elite/blob/main/docs/4.1.6-document-map.md).

## The reference freshness stamp

Each reference document, (3+n).4.x, carries a **freshness stamp** under its
title: the commit its contents were last checked against the code (Tile Lite
Elite's 4.4.7 has none yet). Only reference documents have one, because they
make the falsifiable claims ("these are the columns", "this is every endpoint")
that go silently wrong when the code moves. When you re-verify a document,
update it; an edit alone leaves it as it is.

Re-verification is the weekly `reference-review` activity
([1.4](1.4-programme-activities.md#the-register)), against every file a document
describes.

## Who each range is for

### Every section has an audience and a use case

The audience and the use case decide what belongs in a section. The test for a
sentence is *would this reader do the wrong thing without it*.

| range | who is reading | what they are doing | so it carries | and leaves out |
| --- | --- | --- | --- | --- |
| (3+n).1 | somebody new to the system, or deciding scope | working out what the thing is and where it is going | the current shape, and the direction | how it came to be this way |
| (3+n).2 | whoever is about to change a functional area | making a change without rediscovering the model | the model, its constraints and what the constraints cost, with design notes on rejected ideas a reader might propose | step-by-step instructions, which belong in (3+n).3 |
| (3+n).3 | whoever is building, releasing or operating the application now | doing the next step correctly, under time pressure | the command first, the reasoning below it | anything that delays the reader in a hurry |
| (3+n).4 | somebody who already knows what they want | looking one fact up and leaving | every value, complete and current, with a freshness stamp | reasoning of any kind |
| 1.x | whoever is at a process step, a future project reusing the process and whoever needs to know how the programme is organised | doing the step correctly, and judging whether the process is right | the rule first, the reasoning below it | the programme's history. The portable rule stays separable from the programme's answer to it |
| 2.x, 3.n.x | whoever reviews the programme or an application, and the tooling that reads the records | looking up what happened, what a register holds or how a change was designed | each entry in its template's shape, where it has one; a change document is as [its folder's README](../applications/tile-lite-elite/3.1.7-changes/README.md) says | anything its template leaves out |

`CLAUDE.md`, the skills and the agent files are read by Claude at the moment of
acting, and follow the 1.x row: the rule first, and only what the step needs.

**The one that is easiest to get wrong is (3+n).3**, because the same document
serves somebody shipping in 10 minutes and somebody deciding whether the
process is right. Tile Lite Elite's `docs/4.3.3` is the worked example: a
table of the steps at the top, then each step with where it runs, its commands
and what proves it worked, then Part 2 for the mechanisms behind them.

### Brevity is the use case

Cut a sentence the reader would not miss, and a point already made.

## How these documents are written

### Reader first

**Write first for somebody who needs to do something quickly and wants
pointing at what they need**, and serve every other reader afterwards. That
reader has a job in progress and knows roughly what they want. So: the command
or the rule first, an index by *intent* and the reasoning below it, where
anyone who wants it finds it and anyone else skips it.

The reader who wants to understand *why* is served by the same arrangement,
because reasoning gathered in one place reads better than reasoning scattered
through instructions. Mixing the two fails both readers.

### Give a commit's app version alongside its id

For a commit to an application, `25e9e09` alone dates a change only for somebody willing to go and look it up;
`25e9e09` (app 0.4.12) places it in the release history a reader already
carries. The id stays, because it is the thing you can `git show`.

### Reference answers "what is there" and "what do I type"

The why belongs in an overview section or a (3+n).2 design document, so a
reader looking up a command reads only the command.

### Imply the rationale

Carry the reason in an adjective where one will do: "the safe default", "one
throwaway worktree", "a single source of truth".

### Keep the evidence, not the argument

Keep a fact somebody would otherwise have to go and re-acquire, and drop the
case once made for a decision: reasoning ages, and evidence does not. The
evidence is usually one of four kinds:

- **A measurement** that was expensive to take, or is not repeatable now.
- **A negative result**: what was tried and did not work, which the current
  state cannot show.
- **An outside constraint** the artefact does not reveal: what a service will
  not do, what a tool does when you get it wrong.
- **The failure a guard exists to prevent**, without which the guard looks
  like caution and gets removed.

### Issue numbers, rarely and for a reason

Cite an issue only where a reader would change something wrongly without it.
These documents describe what is there, and provenance lives in commit
messages, which are permanent and carry their own context.

One case qualifies, guiding a future change: a design note on a rejected idea
may cite the issue that argued it, when a later change would otherwise undo the
reasoning without knowing it existed. Change documents are about a change, so they name it.

### Describe the choice made; rejected ideas go in design notes

The descriptive text says what is done: "the tests change the dates in the
database". An aside naming a dropped option goes stale when the decision
changes.

Where a rejected option carried a real constraint, keep the constraint and drop
the comparison: "It must be in-module: backdating needs `state.db`" stays true
when the alternative is forgotten.

In a living document, (3+n).1 to (3+n).3 or 1.x, a rejected idea is written down only
where it is not obvious and somebody might propose it. It then goes in a
closing `## Design notes` section: one short entry each, with the constraint
that ruled it out. Change documents record what was rejected and why, as
[their folder's README](../applications/tile-lite-elite/3.1.7-changes/README.md)
says, and this rule leaves them alone.

### Say what is the case, not what is not

A positive statement replaces *never*, *not only*, *not just*, *rather than*,
*instead of*, *no longer* and the like wherever it says the same: "each
environment has one database" in place of "there is never more than one". A
rule that forbids something is still written as one.

### Say what is, not what should be

*Should*, and a *may*, *typically* or the like qualifying a fact, describe an
intention or hedge a fact; a *may* granting a permission is a rule. "Each environment has
one SQLite database" beats "the project should use one primary database file per
environment".

## Deviations from Google

Each is where the house differs from Google's guide, with its reason.

### British spelling

British spelling, with -ise endings (*organise*, *realise*): the owner's
choice, and the documents' practice.
Names from code, tools and quotations keep their own.

### Dates

ISO 8601, `2026-10-17`: it sorts, and matches the board and the commit stamps.

### Serial comma

No comma before the last *and* or *or* of a list (*red, white and blue*),
unless an item itself contains *and* or *or* and the list would misread
without it: British usage, and the documents' practice.

### Contractions

Full forms (*do not*, *cannot*): a negation stands out in full.

### Dashes

A spaced em dash, `word — word`, for an aside: the documents' practice.

### Quotation marks

Punctuation goes inside the quotation marks only when it belongs to the
quotation: British usage.

### Bold lead sentence

A paragraph may open with its point in bold, so a reader scanning finds it.

### Document numbers as link text

A document's number is its name, so `[1.4](1.4-programme-activities.md)` is
descriptive link text.

### Roles by name

A process document names who acts (the owner, Claude, a reviewer), and *you*
addresses the reader doing a step: several roles read one document.

### Avoid *we*

Avoid *we*, which Google allows for the organisation: it hides which role acts.

## Comments in code

Rust doc comments follow the documentation chapter of the
[Rust API Guidelines](https://rust-lang.github.io/api-guidelines/documentation.html),
and are written as the
[rustdoc book](https://doc.rust-lang.org/rustdoc/how-to-write-documentation.html)
describes. The standard library is the model to copy, at less length. Two of
the guidelines, `C-METADATA` and `C-RELNOTES`, are for crates published to
crates.io, and the programme's crates are unpublished.

Five house rules go with the guidelines.

- **Every public item has a doc comment.** An item that is public
  only as plumbing is made private, or hidden (`C-HIDDEN`), and carries no doc
  comment.
- **An example is given where it shows something the signature does not**,
  applying `C-EXAMPLE` "within reason": the crates have no outside users, and
  an example is compiled and run as a test.
- **A doc comment names the rule it enforces, by its id in the application's
  rules** (Tile Lite Elite's `docs/4.1.0`), so the code, the rules, the design
  documents and the test design point at each other.
- **A doc comment says what else the item changes**: what it persists or
  broadcasts and which state transition it makes.
- **A doc comment links to the numbered document that owns a fact**, in place
  of the fact.

An inline `//` comment says why a line is as it is, where the code cannot. The
history of a decision goes in the commit and the issue, as for documents. The
exception is the failure a guard exists to prevent, kept beside the guard (see
[*Keep the evidence, not the argument*](#keep-the-evidence-not-the-argument)).
An application's comment inventory lists the comments that cite an issue or a
date (Tile Lite Elite's is `scripts/measure/comment-inventory.py`), and the
dated ones are its regression list. Future work goes in an issue.
