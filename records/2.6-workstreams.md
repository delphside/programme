# 2.6 Programme workstreams

The programme's own workstreams, which manage the programme itself: Process
Definition, Programme Tooling and Delivery Tooling. They are generic workstreams
([1.3](../docs/1.3-workstreams.md)) of the programme, so their register is here
and each application's `3.n.4` links to it. The form is the
[workstream-register template](../docs/templates/workstream-register.md).
Which repository a tooling path is in is stated in
[1.1](../docs/1.1-programme-tooling.md).

## The programme's workstreams

| Workstream | Instance of | Owns |
| --- | --- | --- |
| Process Definition | the same | every process, and the documents that state it |
| Programme Tooling | the same | the board, the documentation gates, the git hooks and Claude's tooling |
| Delivery Tooling | the same, at programme level | the generic deliver tool |

The generic workstreams with no instance here:

| Workstream | Why |
| --- | --- |
| Application Architecture, Client, Client Distribution, domain workstreams | The programme has no application of its own. |
| Security & Access | The programme has no accounts or identity of its own; Process Definition owns the security policy. |
| Operations & Infrastructure, Capacity & Performance | Each is one workstream across every application, registered in [3.3.4](../applications/infrastructure/3.3.4-workstreams.md). |

### Process Definition

How the programme works: how a change is raised, classified, agreed, built,
tested, delivered and reviewed, the roles, and the documents that state it.
The test manager decides the test strategy's content
([1.7](../docs/1.7-roles-and-responsibilities.md#test-manager)).

### Programme Tooling

The tooling the programme manages itself with: the board, the documentation
gates and the map, the digest and reports, the git hooks, and Claude's skills,
agents and hooks.

#### The artefacts Programme Tooling owns

| Artefact | For |
| --- | --- |
| the programme repository's `scripts/` with its tests, except `scripts/deliver/` and `scripts/tests/deliver-*.bats` | the board model, the documentation gates, the reports |
| `config/programme.toml` | the programme's own settings |
| [`docs/1.1`](../docs/1.1-programme-tooling.md), [`docs/1.6`](../docs/1.6-github-project-board.md) | the programme's tooling, and the board's types, fields and the strings tooling matches |
| the issue types, fields and option values | what the board is built from |
| `.github/workflows/` | the programme's workflows, as registered in [1.1](../docs/1.1-programme-tooling.md) |
| `.githooks/` | the hooks that run at commit and merge time |
| `.claude/` | Claude's skills, agents and hooks; each skill links to the rule it applies |

### Delivery Tooling

The machinery from a commit to a running environment, for every application
with an `app-profile.toml` `[deliver]` section. A change to it takes a branch,
and a run on preview or rehearsal before it merges
([1.1](../docs/1.1-programme-tooling.md#two-kinds-of-tooling)).

#### The artefacts Delivery Tooling owns

| Artefact | For |
| --- | --- |
| `scripts/deliver/` with its `scripts/tests/deliver-*.bats` tests | the generic deliver tool: building, deploying, releasing and rolling back |

Each application's own delivery scripts are its Delivery Tooling instance, and
Tile Lite Elite's `scripts/deliver/issue-mentions.sh` is among them: its
`deploy.sh` sources it.
